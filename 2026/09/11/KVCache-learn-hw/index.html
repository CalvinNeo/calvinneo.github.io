学习 KVCache：硬件和架构

发表于 2026-09-11 |

在设计 KVCache 的时候，需要考虑我们能接触到的硬件的性能，在作出设计，包含显卡、网卡、HBM、DRAM 和 SSD。

基础知识

大模型生成回答时，会不断用到前面的上下文。在常规 Transformer 中，attention 会为历史 token 保存 Key 和 Value 两类向量，也就是 KVCache。保留这些向量后，生成下一个 token 时就不用把历史 token 的 K/V 重新计算一遍。代价是上下文越长、同时处理的请求越多，KVCache 占用的内存也越大。

为了理解后面的取舍，可以把一次推理分成两个阶段。Prefill 是处理输入提示词、建立其 KVCache 的阶段。Decode 是利用已有 KVCache，逐步生成后续 token 的阶段。对于读取全部历史上下文的注意力计算，也就是本文所说的 dense attention，历史 KV 会在后续 decode 中反复被访问。

既然要反复读，最直接的办法就是把活跃请求的 KV 放在 GPU 的 HBM 中。HBM 是 High Bandwidth Memory，也就是高带宽内存，通过封装内的宽接口连接 GPU。它很快，但容量有限，而且模型权重、计算临时数据也要占用它。因此，HBM 用完之后，系统通常会考虑把暂时不用的 KV 搬到 CPU 内存，或者保存到其他机器上，以便之后再取回来。

本文把 CPU 一侧的普通系统内存简称为 DRAM，也会称它为 Host 内存。严格说，HBM 本身也是一种 DRAM 技术，这里的区分是为了说明数据放在 GPU 旁边，还是放在 CPU 一侧。NIC 就是网卡，CX-7 和 CX-8 是 NVIDIA ConnectX 系列网卡的两个代际。跨机器共享 KV 时，网卡负责把这些数据运过去。

由此会出现两个不同的问题。第一个是“有多少空间可以保存 KV”，这是容量问题。第二个是“GPU 要用的时候，能不能及时把 KV 搬回来”，这是带宽和延迟问题。增加 DRAM 可以解决一部分容量压力，但不会自动缩短搬运时间。

后文提到的 KV 恢复，泛指把一个推理请求要用的 KV 从本地或远端 DRAM 加载到 GPU。它可能是新请求复用了缓存前缀，也可能是暂停的请求重新开始执行。一个推理请求可以分布在多张 GPU 上，一次恢复也可以拆成很多次传输。

速度差距

当 KV 已经在 GPU 的 HBM 中时，GPU 通过本地内存接口读取它。当 KV 在本机 CPU 内存中时，需要通过 PCIe 搬到 GPU。PCIe 是连接 CPU、GPU、网卡等设备的高速互联。如果 KV 在另一台机器，还需要先跨越网络，再经过目标侧的设备连接到达 GPU。

这几种路径的物理条件不同。HBM 紧邻 GPU，可以使用大量并行的短距离连接。PCIe 要连接板卡和主机，网络还要连接不同机器，接口规模、传输距离和可靠性要求都不同。因此，GPU 读取本地 HBM 的速度远高于从外部获取数据，是很自然的结果。

详细说明

用这张表估算 KV 搬运时，最重要的是选对路径和方向。比如，从 CPU 内存往 GPU 写入一份 KV，只能使用 PCIe 的一个方向，不能拿双向合计的 126 GB/s 来算。数据已经在 B200 的 HBM 中之后，GPU 才能通过本地内存接口反复读取它。此时的标称上限是 8 TB/s = 8,000 GB/s，与从外部搬进来的速度属于两条不同路径。

表里的“峰值”也不等于应用实际能拿到的速度。接口上传输的内容除了 KV 本身，还有报头、控制信息和用于保证可靠性的冗余数据。设备排队、访问模式以及软件提交是否及时，也会影响最后测到的吞吐。因此，做容量规划时可以参考规格，估算请求延迟时则应尽量使用实测的有效带宽，也就是每秒真正搬完了多少 KV 字节。

如果想进一步理解为什么 PCIe 的数字不是整齐的 32、64、128，可以从 PCIe 5.0 ×16 看起。×16 表示这条连接有 16 条并行 lane，也就是传输通道。Gen5 是 PCIe 5.0 的简称，每条通道的原始单向速率是 32 Gb/s，但它采用 128b/130b 编码，即每 128 bit 内容需要占用 130 bit 传输空间。因此，扣除这部分开销后得到：

PCIe 4.0 每条通道的速率是 Gen5 的一半，所以同样计算得到约 31.5 GB/s。这些数值还没有扣除 TLP（Transaction Layer Packet，事务层数据包） 的开销。TLP 是 PCIe 用来表达内存读写等操作的数据包，其中除了数据，还要携带地址、操作类型等信息。也就是说，表里的 63 GB/s 依然不是应用有效吞吐。

PCIe 6.0 在更高速度下还要兼顾传输可靠性，因此引入了固定大小的数据打包和纠错机制。FLIT（Flow Control Unit，流控单元） 是链路使用的固定大小传输单元，PCIe 6.0 将其定为 256 byte。FEC（Forward Error Correction，前向纠错） 则通过附加冗余信息，让接收方能直接纠正一部分传输错误，减少重传。一个 FLIT 中也要容纳控制和校验信息，所以 256 byte 不会全部用于承载应用数据。这就是表中 128 GB/s 被标为“原始带宽”的原因。理解 KV 搬运时，不必记住它们的每个字段，只需要知道可靠传输会占用一部分链路能力。PCI-SIG 对 FLIT 和 FEC 的解释

关于 GDR

跨机器读取 KV 时，如果每一批数据都需要 CPU 执行网络收发、拷贝和转交，CPU 开销和额外内存访问就可能拖慢过程。RDMA（Remote Direct Memory Access，远程直接内存访问） 允许网卡直接访问事先授权和注册的内存，从而减少 CPU 对数据搬运的参与。这里的“注册”是把指定内存区域及其访问权限交给网卡，并不是把数据复制一份。

GPUDirect RDMA 把这条直接访问路径延伸到 GPU 显存。在硬件和驱动支持的情况下，远端数据可以由目标网卡直接写入 GPU，不必先落到目标机器的 CPU 内存，再进行一次 CPU 内存到 GPU 的复制。下面将它与另外两条路径对比，其中本地复制可以通过 CUDA，也就是 NVIDIA 的 GPU 编程与运行时平台来发起。

GPUDirect RDMA 省掉的是目标侧的内存中转，并没有省掉网卡到 GPU 的 PCIe 连接。远端取数、网络传输和目标 GPU 接收数据仍然要花时间，所以整体速度取决于这条路径中最慢的一段。NVIDIA GPUDirect RDMA 文档

实际服务器还需要考虑设备接在哪里。多路 CPU 机器的内存通常分属不同 CPU，本地访问与跨 CPU 访问的代价不同，这就是 NUMA（非统一内存访问）。同样，多个 GPU 和网卡也可能共用 PCIe 交换芯片及其上行连接。即使每个设备单独测试都很快，并发时仍可能争用同一条通道。后面计算多 GPU 的总带宽时，必须说明是否存在这种共享瓶颈。

关于网卡

升级网卡的直接收益是提高网络这段的传输能力。CX-7 的 400G 配置单向为 50 GB/s，CX-8 的 800G 总速率配置则为 100 GB/s。只有原来的瓶颈确实在网络上，而且源端取数和目标端写入都能跟上时，KV 搬运才可能获得接近两倍的提升。

先看端口。InfiniBand 和 Ethernet 是两种不同的网络体系，RDMA 可以在它们上面实现，但可用的端口速率不一定相同。当前官方手册列出的 CX-8 C8180 支持单端口 800G XDR InfiniBand，XDR 是这里的 InfiniBand 速率代际名称。它的 Ethernet 配置包括两个 400GbE 端口，C8240 的默认配置也是两个 400GbE 端口。因此，在这类 Ethernet 配置下，单向 100 GB/s 是两个端口加起来的能力，每个端口仍是单向 50 GB/s。搬运软件必须把工作分配到两个端口，才能利用整卡总带宽。CX-8 官方端口配置

再看网卡接入主机的通道。CX-8 支持 PCIe 6.0 ×16。如果服务器只有 PCIe 5.0，适用的 Socket Direct 型号可以通过辅助卡和线缆，额外接入一条 PCIe ×16 连接，让网卡使用两条 Gen5 路径的总 I/O 能力。它解决的是单条 Gen5 ×16 带宽不足的问题，需要对应的网卡、插槽和配件。只插一条 Gen5 ×16 时，经过该连接的数据仍受约 63 GB/s 的单向理论上限约束。CX-8 接口与 Socket Direct 说明

最后还要看 GPU 怎样接收数据。即使网卡已经接在 Gen6 上，如果某个请求的 KV 全部要写入同一张、仅通过 Gen5 ×16 接收数据的 GPU，这条 GPU 连接仍会限制速度。多个 GPU 分担传输时，可能利用上更高的网卡总带宽，但前提是这些 GPU 的连接没有再汇聚到一条更窄的共享通道上。因此，换成 CX-8 后不能直接把所有恢复耗时除以 2。

KVCache 的架构比较

比较实现方案时，先问“这份 KV 接下来会怎样被使用”通常比先选传输库更有用。如果它马上要被连续读取几十次，放在 HBM 的价值很大。如果它只是可能被未来请求复用，放在更便宜的 DRAM 中通常更合适。

在这个前提下，各种方案可以理解为对“容量、第一次等待时间、后续重复访问成本”的不同取舍。

方案 为什么会选择它 为此要付出什么
活跃 KV 留在 HBM 后续每个生成步骤都能直接访问本地内存，适合对响应速度要求高的请求。 需要为当前请求保留显存，能够同时容纳的上下文和请求数有限。
本机 DRAM 保存 KV，用时再搬入 HBM 利用本机较大的内存扩充缓存，命中后只需经过本地设备连接。 加载速度受 PCIe 和内存位置影响，也不能天然与其他机器共享。
远端 DRAM 保存 KV，直接写入目标 HBM 多个推理实例可以复用同一批历史 KV，并省掉目标侧内存中转。 请求开始计算前要等待网络搬运，还可能与其他 GPU 通信争用网卡。
远端 KV 先放本机 DRAM，再搬入 HBM 可以提前从远端取回数据，并在本机留下后续可复用的副本。 第一次使用需要两段搬运，本机内存也要额外读写一遍。
Prefill GPU 直接把 KV 交给 Decode GPU 把处理提示词和生成回答交给不同 GPU，以便分别调度这两类工作。 源 GPU 必须等传输完成才能释放对应数据，跨节点交接仍受网络限制。
每步计算前从 DRAM 读取所需 KV 即使 GPU 装不下全部历史 KV，也能继续运行较长上下文。 同一份历史 KV 可能被反复搬运，每个 token 的生成时间容易受外部带宽限制。
更冷的 KV 放到 NVMe SSD 对很久以后才可能复用的数据，用 SSD 换取更大的低成本容量。 SSD 还引入存储 I/O 等待，需要更早预取并单独评估恢复时间。

其中，把 prefill 和 decode 分给不同 GPU 的方式通常叫 P/D 分离。把 GPU 内存中的数据转移到 CPU 内存或存储设备，通常叫 offload，也就是卸载。表中的 NVMe 是访问固态硬盘的协议，NVMe SSD 在这里承担较慢但容量更大的存储层。这些设计可以组合使用，例如活跃 KV 留在 HBM，历史前缀保存在共享 DRAM，更冷的数据再下沉到 SSD。

这里还要区分两种收益。前缀缓存是在模型、位置等计算条件兼容时，复用已有提示词前缀的 KV，从而省掉这一段 prefill。它并不会自动减少后续 dense decode 对历史 KV 的读取，所以前缀命中率提高，通常首先影响的是请求开始生成之前的等待时间。vLLM 前缀缓存说明

已有系统也遵循这种思路。SGLang HiCache 把 GPU、Host 内存和共享存储组织成多层缓存，并支持预先取回后面要用的数据。Mooncake 则围绕共享 KV 组织存储和推理调度。它们提供了可参考的实现方式，但具体收益仍要放回自己的请求复用模式和硬件路径中判断。HiCache 设计、Mooncake 论文

搬一份 KV 要多久：从输入假设算到结果

为什么先用“字节数除以带宽”估算

对已经建立连接的大块传输，最基本的关系就是“耗时 = 数据量 ÷ 有效带宽”。它能先告诉我们数量级是否可行。例如，单靠更快的索引查询，不可能把一次需要百毫秒才能搬完的数据传输压到几毫秒。

本节用 CX-7 和 PCIe 5.0 构造一个简化算例。下面的两个带宽是为了演示计算而选的参数，属于计算假设，不是实测结果或设备保证达到的速度。

输入参数 算例取值 为什么取这个值
每张 GPU 的本地 DRAM→HBM 有效带宽 Bp 50 GB/s Gen5 ×16 扣除编码后的理论值约为 63 GB/s。算例进一步留出约两成余量，取方便计算的 50 GB/s。
每张 CX-7 可用于远端 KV 搬运的有效带宽 Bn 40 GB/s 400G 单向标称速率是 50 GB/s。算例同样留出两成余量，取 40 GB/s。

这两个余量只是演算选择，不能用来推断所有服务器都具有固定的 80% 利用率。HBM→Host DRAM 的速度也可能与 Host DRAM→HBM 不同，所以这里的数字仅用于讨论把 KV 加载到 HBM 的方向。

设总搬运量为 S，同时接收数据的 GPU 数为 G，能够独立提供带宽的网卡数为 N。如果各张 GPU 的 PCIe 路径都能并行工作，本地总带宽就是 G × Bp。远端传输还要经过网卡，因此它受网络总带宽 N × Bn 和 GPU 总接收能力中较小的一项限制。

最后一条之所以相加，是因为它假设先把整份 KV 从远端搬到本机 DRAM，然后才开始往 HBM 搬。若改成分块流水线，第一块写入本机 DRAM 后就立即开始向 HBM 复制，同时接收第二块，两段工作就有机会重叠。理想情况下，总时间可以趋近于较慢的那一段，再加上流水线启动和收尾所需的时间。这里重叠的是不同块的搬运，同一块仍要先完成本机 DRAM 接收，才能开始第二段复制。

为简化比较，公式还用同一个 Bp 表示两种路径向 HBM 写入的带宽约束。真实机器上，本地 CUDA 拷贝和 GPUDirect RDMA 的有效带宽可能不同，规划时应分别测量，不能拿本地拷贝结果直接代替直达路径的结果。

为了把路径本身的差别看清楚，这组计算采用以下前提：

  • 准备工作已完成。 数据已经准备好，连接已经建立，所需内存也已注册。
  • 传输资源没有额外竞争。 没有其他业务抢占算例中的带宽。
  • 多卡可以并行。 数据均匀分配，源端内存、两端网卡、网络和 PCIe 都能提供所需的并行能力。

真实服务还要加上排队、查询、校验和同步等时间，因此这些计算不是请求完成时间的保证值。

第二行最能说明共享网卡的影响。八张 GPU 各自通过本地路径搬 4 GiB，理想情况下可以并行，所以仍是 85.9 ms。但从远端搬入时，一张 CX-7 要负责全部 32 GiB，时间变成 32 × 2^30 ÷ (40 × 10^9) ≈ 859.0 ms。如果再经本机 DRAM 整批中转到 HBM，就在此基础上加 85.9 ms，得到约 944.9 ms。这里网络这段已经比本地加载慢约十倍，原因是总数据量增加了八倍，网卡总带宽却没有增加。

第三行把网卡也增加到八张，网络总有效带宽在假设下变成 8 × 40 = 320 GB/s。于是 32 × 2^30 ÷ (320 × 10^9) ≈ 107.4 ms，回到了第一行的时间。这个结果要求源端和目标端都能提供相应的总带宽，而不只是目标机器插了八张网卡。

至于 Host 中转，它的代价取决于实现是否流水化。第一行的 193.3 ms 是两段整批串行的结果。如果分块后能够充分重叠，两段分别需要 107.4 ms 和 85.9 ms，整体就可能接近较慢的 107.4 ms，再加启动和收尾时间。不过，本机 DRAM 仍然要先写入 4 GiB，再读出 4 GiB。若这两段争用同一组内存或 PCIe 资源，就不能假设它们同时达到独立测试时的带宽。

为什么已经能流水化，仍然希望绕过本机 DRAM

因为系统要优化的不只是一次传输的完成时间，还包括完成它要占用多少共享资源。流水线让两段工作同时进行，GPUDirect RDMA 则省掉了本机 DRAM 中转这份工作。 如果内存和设备连接都很空闲，被重叠的工作可能不影响这次请求的耗时。并发上来之后，它仍然要和其他请求争用资源。

先沿用前面的 4 GiB 算例看一次传输。假设网络有效带宽为 40 GB/s，本机 DRAM→HBM 为 50 GB/s，而且二者并发时不降速，那么充分流水化的中转路径确实可能接近直达 HBM 的 107.4 ms。原因是网络更慢，后面的复制能够跟上接收速度。因此，不能拿整批串行的 193.3 ms 来断言“绕过 DRAM 一定能快这么多”。在这组假设下，直达路径的主要收益会体现在资源消耗和并发余量上，单次大块传输的吞吐未必明显提高。

这些额外资源消耗来自哪里？网卡先把收到的 KV 写入本机 DRAM，随后复制引擎再把相同的数据读出来，写入 HBM。以同一份 4 GiB KV 为例，按有效载荷统计，两条路径的工作量如下。表中的本机指接收端，不包含远端源 DRAM 的读取，也不包含报头和控制信息。

接收端需要完成的工作 直达 HBM 本机 DRAM 中转，包括流水化实现
接收网络上的 KV 数据 4 GiB 4 GiB
向本机 DRAM 写入中转 KV 0 4 GiB
从本机 DRAM 读出中转 KV 0 4 GiB
最终写入 HBM 4 GiB 4 GiB

因此，中转多出了 4 + 4 = 8 GiB 的 Host 内存读写工作量。这里的 8 GiB 是累计流量，不是需要分配 8 GiB 缓冲区，分块循环使用缓冲区可以降低容量占用。表里的 0 也只表示没有这份 KV 的中转读写，软件元数据和控制逻辑仍然会使用 Host 内存。实际 DRAM 芯片上的总线流量还会受缓存和平台实现影响，这张表是在说明有效载荷的去向。

如果持续以算例中的 40 GB/s 接收 KV，中转路径就需要同时承接约 40 GB/s 的 Host 写入和 40 GB/s 的 Host 读取，合计约 80 GB/s 的读写需求。多张网卡、多张 GPU 同时恢复 KV 时，这些需求会继续叠加，还可能与 CPU 业务共用内存控制器或跨 NUMA 连接。一旦并发使任一段变慢，原来“可以完全重叠”的前提就不成立，缓冲区会积压，请求也会排队。这就是即使单请求耗时相近，直达路径仍可能具有更好并发能力、让最慢那部分请求等待更少的原因。

中转还增加了一次传输交接。软件需要知道某块数据已经接收完成，再提交或触发 DRAM→HBM 复制，并等复制完成后才能复用缓冲区。这里的复制通常可以由 DMA（Direct Memory Access，直接内存访问） 硬件完成，不必让 CPU 逐字节搬运，但任务提交、完成通知和缓冲区管理仍然存在。流水线稳定运行后可以隐藏一部分等待，第一块的交接和最后一块的收尾却仍要完成。直达路径也需要内存注册和正确的完成、可见性同步，只是省掉了这次 Host 中转交接。

至于 PCIe 能省多少，要看设备怎样连接。例如网卡和 GPU 挂在同一块支持设备间直连的 PCIe 交换芯片下时，数据有机会在交换芯片内转发，减少经过 CPU 侧上行连接的流量。但这不是所有机器都具备的条件，也不能概括成“所有 PCIe 流量都减半”。最终进入 HBM 的那份数据仍然要经过 GPU 的接入路径，选择方案时需要核对拓扑并测量。NVIDIA GPUDirect RDMA 的路径与拓扑约束

最后再看什么时候值得保留本机 DRAM 中转。以下几种情况中，它承担了额外职责：

  • 本机还需要缓存这份 KV。 如果后续请求可能再次复用，写入 DRAM 就同时完成了缓存填充。
  • 需要提前预取。 如果 HBM 暂时没有空位，本机 DRAM 可以先接住数据，让网络搬运提前开始。
  • 需要 CPU 处理数据。 数据先进入 Host 内存，可以配合 CPU 完成处理，再送入 HBM。
  • 直达路径不适用。 如果硬件、驱动或设备连接不适合 GPUDirect RDMA，中转可能更合适。

所以，当数据已经可以直接写入 HBM，而 Host 副本又没有后续用途时，通常优先考虑直达路径。若本机 DRAM 承担了缓存、预取或处理职责，就应把这些收益一起纳入比较。

为什么缓存装得下，还可能来不及服务请求

前面的计算讨论一批数据搬多久。持续接收请求时，还要看单位时间内有多少份数据需要搬。如果一张网卡的有效带宽是 40 GB/s，每次要搬 4 GiB，那么即使完全没有额外开销，它每秒最多也只能完成：

9.31 来自同一组算例参数，不是系统实测的每秒请求数。真实请求大小不同，还可能同时发生写回和其他通信，而且满负载运行会形成排队。因此，DRAM 即使能存下很多份 KV，也不意味着新请求到达时都能及时取出。

这里直接影响的是 TTFT（Time To First Token，首 token 延迟），也就是从请求发出到收到第一个输出 token 的时间。缓存可以省掉一部分 prefill，但若加载 KV 的队列很长，省下的计算时间可能又被等待搬运消耗掉。

做带宽预算时，应分别统计发送和接收方向，再检查它们共享的内部资源。全双工链路允许同时收发，并不意味着两类任务在 CPU 内存、PCIe 上行连接或网卡内部完全互不影响。这也是为什么仅看平均网络利用率，不能判断某个请求是否会被拖慢。

为什么“用之前搬一次”和“每生成一个 token 都搬”差别很大

把历史 KV 放在 DRAM 中是否划算，取决于搬回来之后能用多久。如果一个请求只在开始时加载一次，后面连续生成很多 token，那么这次搬运的成本可以分摊到整个回答。如果每个生成步骤都要从 DRAM 重读同一份历史 KV，成本就会不断重复。

沿用前面搬运算例中的 4 GiB 数据量和 40 GB/s 有效带宽。一次性加载需要约 107.4 ms，此后的历史 KV 读取主要发生在 HBM 内。若改成每步都从外部读取这 4 GiB，那么单步传输就需要约 107.4 ms。假设生成 100 个 token，累计搬运量会达到 4 × 100 = 400 GiB，仅传输就需要占用约 107.374 ms × 100 = 10.74 秒的链路时间。

100 步是为了展示重复访问代价而选的假设。这个比较还固定了历史 KV 的大小，没有计算后续 token 带来的增长，也没有把计算与传输重叠的情况计入总响应时间。但它已经说明，外部缓存能否支持低延迟 decode，首先要看每步到底需要搬多少字节。

如果注意力只访问历史 KV 的一部分，或者有一部分始终留在 HBM，就可以用 f 表示每步需要从外部读取的比例。设全部 KV 大小为 S，外部有效带宽为 B，则这一部分的传输时间约为 f × S / B。如果计算必须等待搬运完成，时间需要相加。如果传输可以和计算充分并行，理想情况下总时间由两者中较慢的一项决定。

为了说明这个约束有多严格，再假设业务希望每 20 ms 生成一个 token，而现有计算已经需要 18 ms。这两个时间是示例中的延迟目标和计算预算，并非某个模型的实测结果。20 ms 对应每个请求约每秒输出 50 个 token，因为 1 秒 ÷ 0.020 秒 = 50。如果传输不能重叠，就只剩 20 - 18 = 2 ms 的额外等待空间。

在 40 GB/s 下，可搬的数据量等于带宽乘以时间，因此得到：

可用于传输的时间 计算过程 能搬的数据量 占 4 GiB 历史 KV 的比例
20 ms 40 × 10^9 × 0.020 byte 800 MB，约 0.745 GiB 0.745 ÷ 4，约 18.6%
2 ms 40 × 10^9 × 0.002 byte 80 MB，约 76.3 MiB 80 × 10^6 ÷ (4 × 2^30)，约 1.86%

第一行表示“如果可以利用整个 20 ms 传输窗口”的理论预算，第二行对应不能与计算重叠时仅剩的 2 ms。真正能利用多少窗口，要看数据依赖。比如，计算第 1 层时，可能同时预取第 2 层的 KV，但第 2 层必须等自己的数据可用才能开始。这样的按层预取可以隐藏部分等待，不能减少必须经过链路的总字节数。

所以，每步从 DRAM 读取 KV 并非一概不可行。若访问足够稀疏、计算本身足够长，或者业务接受更高延迟，它可能是合理的容量换性能方案。判断时应先明确 SLO（Service Level Objective，服务水平目标），例如首 token 要多快、连续输出允许多大间隔，再检查每步搬运量是否落在预算内。异步复制还需要推理引擎正确安排任务依赖和内存生命周期。CUDA 对传输与计算重叠的说明

设计

怎样设计 KV 的保存、换出与恢复

前面讨论了数据放在哪里、搬运需要多久。接下来还要回答一个同样重要的问题：谁决定保存这份数据，什么时候可以复用，又由谁决定释放？这些规则如果没有理清，即使传输带宽足够，也可能出现重复搬运、提前释放或读到尚未准备好的数据。下面从这些约束出发，推导一套分层缓存的设计。

为什么 HBM 和 DRAM 应该分别做容量预算

HBM 要支撑正在运行的计算，DRAM 则要容纳希望保留的历史 KV 和暂时换出的请求。这两类需求由不同因素决定：前者主要取决于模型、上下文长度和活跃并发，后者还取决于历史数据多久会被复用。因此，我们把两层的容量分别配置，再用工作负载推导它们的比例。

具体来说，推理侧先扣除模型权重、激活和临时工作区，确定 HBM 中能够分给 KV 的空间。缓存侧则根据历史数据保留范围、临时换出的峰值和搬运缓冲，确定需要多少 Host DRAM。这样做可以让缓存容量随着复用需求调整，而不必跟着 GPU 总显存机械地翻倍。

比较两层容量时，还需要明确统计范围。应选定同一组推理实例及其可使用的缓存资源，计算真正分给 KV 的容量：

如果一组共享缓存同时服务多组推理实例，应按资源配额或统一的集群范围统计，避免把同一份 DRAM 容量重复算给每一组实例。比例只是描述资源配置的结果，不能代替逐张 GPU 的容量检查。

这是因为并行方式会改变每张 GPU 负责的数据。TP（张量并行）把同一层中的张量计算拆到多张 GPU，PP（流水线并行）则把不同层分给不同 GPU。KV 具体如何分片、是否存在复制，都要按模型布局确定，不能仅凭 GPU 数量就假定每张卡恰好持有相同比例的 KV。

为什么要区分保存历史前缀和临时换出

这两种操作都会把 KV 从 HBM 搬到 Host DRAM，但数据的用途不同：

  • 保存历史前缀，是为未来请求保留复用机会。 当前请求结束后，缓存仍可能有价值，是否保留取决于后续复用需求。
  • 临时换出，是为当前请求暂时腾出显存。 请求还没结束，之后继续执行时仍然需要这些数据。

因此，我们为两类数据分别管理保留期限、查找方式和释放条件。

对于历史前缀，重复写入已经存在的数据只会消耗带宽和容量，所以保存前先检查目标缓存中有没有可复用的部分，只补齐缺失的块。为了让后续请求找到这些数据，需要维护前缀索引，也就是从提示词前缀及模型、位置等兼容条件，映射到对应缓存块的记录。只有数据已经准备好、能够被正确读取后，才把对应条目标记为可用，避免后续请求命中一份尚未写完的 KV。

临时换出的第一目标则是保证当前请求能继续执行。因此，换出过程需要保留请求与数据块的对应关系，并在目标副本准备好之前保留源数据。之后恢复时，再分配 HBM、加载所需 KV，确认数据可供计算使用后，才释放不再需要的临时 Host 副本。临时副本默认服务于原请求，如果还希望让其他请求复用，就需要另外满足前缀匹配和兼容性条件，并纳入共享缓存的管理。

这也解释了为什么我们把“保存完成”和“释放源块”设计成两个独立事件。保存后的 HBM 副本可能仍被当前计算或其他请求使用，而从历史缓存加载到 HBM 后，Host 副本也可能继续服务其他请求。只有所有使用者都不再依赖某个物理块时，才能回收它。

失败时的处理也要服从数据用途：

  • 历史前缀保存失败： 可以选择放弃这次缓存机会，让未来请求重新计算。
  • 临时换出失败： 如果之后还要恢复这个请求，就必须保留可用副本，或者明确安排重算。提前回收唯一可用的副本，会让请求失去继续执行所需的数据。

为什么 DRAM 不需要成为 HBM 的完整镜像

分层 KV 缓存要保存的是值得保留的 KV。HBM 中的模型权重、普通激活和临时工作区属于其他内存用途，不会因为引入 KV 缓存就自动复制到 DRAM。即使只看 KV，需要保存的范围也取决于后续用途，因此没有一个固定的“HBM 内容有多少百分比必须同步到 DRAM”。

因为数据可以被多个请求共享，又可以只补齐缺失部分，统计时需要区分三个量：

  • 新增搬运量： 本次真正经过链路传输了多少数据，用来判断带宽需求。
  • 缓存覆盖量： Host 缓存已经能够提供多大范围的 KV，包括之前就已存在的部分。
  • 两层重复驻留量： 当前有多少 KV 同时在 HBM 和 DRAM 中保存了副本，用来判断容量利用率。

把它们混在一起，会同时误判带宽需求和容量利用率。

可以用一个假设例子说明。假设准备保存的 token 范围对应 10 GiB KV，目标缓存已经有其中连续匹配的前 6 GiB。那么新增搬运量约为 10 - 6 = 4 GiB，保存完成后，Host 缓存可覆盖的范围是全部 10 GiB。这三个数字只是为了说明增量保存，忽略了块对齐和元数据开销。如果同一范围的 HBM 副本仍然驻留，两层就暂时重复保存这 10 GiB。之后 HBM 块被回收，Host 副本仍可以继续保留。

为了便于分配、复用和回收，我们可以把一组 token 的 KV 组织成一个缓存块。这会让实际占用受到块边界影响，例如最后一块可能没有填满。因此，容量预算应统计实际分配的块，搬运预算应统计真正传输的字节，两者不必完全相等。

数据表示也会影响这些数字。如果两层保存相同布局、相同精度的 KV，同一范围的有效数据量通常相近。如果为了节省 Host 空间而改用压缩表示，就要同时考虑压缩和恢复的成本。低精度表示还可能需要保存解释数值的缩放系数等辅助数据，不能只统计 K/V 数组本身。这里的设计原则是按实际表示计费，并确认恢复后的数据满足计算要求。

为什么拆成多个传输块，还不等于计算已经能流水化

要让 GPU 计算第 1 层的同时接收第 2 层，推理引擎必须知道第 1 层的数据何时已经可以安全读取。仅仅把传输拆小，或者并发提交多个复制任务，并不会自动建立计算与数据之间的依赖关系。

因此，我们需要把“数据可以使用”作为明确的接口语义。这里的可见性是指后续 GPU 计算能够正确读取新写入的数据，不能仅凭发送端报告传输完成就作出判断。具体需要哪些同步操作，应遵循所用传输方式、驱动和运行时的要求。NVIDIA GPUDirect RDMA 同步说明

一种便于实现的方案是整批加载完成、满足同步要求后再开始计算。要进一步重叠，就让搬运层按可消费的粒度报告就绪状态，例如通知某一层的 KV 已可读取，再由推理调度启动依赖它的计算。设计这个过程时，需要明确几项条件：

  • 源数据的生命周期： 在复制结束前，源数据不能被释放或改写。
  • 目标数据的生命周期： 在依赖它的计算结束前，目标块不能被复用。
  • 就绪通知的含义： 通知应保证计算可以安全读取数据。如果设计包含完整性校验，还要明确校验通过是否也是就绪条件。

这种优化改变的是任务依赖和等待的位置。我们可以让不依赖同一份数据的工作先运行，但仍需保留真正的数据依赖。只有这样，较短的接口返回时间才有机会转化为完整请求的加速。

HBM 和 DRAM 配比，为什么应该从工作负载推导

先算正在运行的请求需要多少 HBM

HBM 首先要满足正在运行的计算。因此，规划 KV 容量的起点应该是扣掉模型权重和运行开销后还剩多少，而不是先套用一个 HBM:DRAM 比例。

接下来估算请求需要多少 KV。对于常规 GQA（Grouped-Query Attention，分组查询注意力），多个查询头会共享一组 K/V，因此应使用实际的 KV head 数计算，而不是查询头数。一个 KV head 可以理解为每层为每个 token 保留的一组 K/V 向量，head_dim 就是每个向量有多少个元素。

这里换用一个更大的假设配置，说明容量怎样随模型变化：80 层、8 个 KV head、每个向量 128 个元素，BF16 每元素占 2 byte。它与前面“每张 GPU 加载 4 GiB”算例中的假设相比，只把层数从 32 改成了 80，所以每 token KV 也变成原来的 80/32 = 2.5 倍。

选择两个上下文长度，再加一个并发数，就能得到以下容量。8,192 和 32,768 是本文使用的两个示例长度，64 是假设的并发请求数，都不是部署默认值。

假设工作负载 计算方式 全模型 KV 数据量
一个请求，8,192 个 token 320 KiB × 8,192 2.5 GiB
一个请求，32,768 个 token 320 KiB × 32,768 10 GiB
64 个请求，各有 32,768 个 token 10 GiB × 64 640 GiB

这张表算的是整个模型需要保留的 KV。真正分配到多张 GPU 时，还要看每张卡负责哪些层、哪些 head，以及有没有数据复制。不能只把总量除以 GPU 数就认为每张卡都能装下，应该逐张检查。工程上常把这些参与并行计算的进程称为 rank，容量规划也需要按各个 rank 的实际布局核对。

上述公式的适用条件是使用常规 K/V 表示。比如 MLA（Multi-head Latent Attention，多头潜在注意力） 会采用压缩的潜在表示，稀疏注意力也可能改变实际保留和读取的数据量。模型量化、附加索引、缓存块未填满和请求间共享前缀，都可能让物理占用偏离这个简单公式。因此，实际分配容量时，应使用模型真实的块大小与块数量计算。

DRAM 主要为哪些数据留空间

DRAM 承担的任务与 HBM 不完全一样。除了容纳临时换出的活跃请求，它更重要的用途是保存未来可能复用的历史 KV。因此，应该先观察这些历史数据多久会再被访问，以及在希望保留的时间窗口内总共有多少不重复的数据。

“唯一”指去掉共享前缀等重复内容后的数据。同一前缀被很多请求复用时，不应把它按请求数重复算一遍。反过来，如果为了跨节点可用性保留多个物理副本，就需要把每个副本占用的空间算进去。若某一份 KV 在 HBM 和 DRAM 中都有副本，两边容量相加也不等于可保存的不同数据总量。

为什么不能直接给出一个最佳比例

两个系统即使使用同样的 GPU，合适的 DRAM 大小也可能完全不同。一个系统的用户反复访问相同长前缀，多保留历史 KV 可能节省大量计算。另一个系统的请求几乎不重复，增加 DRAM 可能只会存下更多再也用不到的数据。

在没有访问统计时，可以先用 D_KV/H_KV = 2 做一次容量实验，再测试 1 和 4，观察 DRAM 每翻倍一次还能带来多少收益。这里的 1、2、4 是为了观察容量翻倍效果而选的实验点，不代表推荐配置或通用最佳比例。如果已有请求记录，优先根据实际复用间隔估算需要保留的数据量。

例如，假设八张 GPU 每张实际能给 KV 分配 80 GiB，那么 H_KV = 8 × 80 = 640 GiB。若先测试 DRAM 是它的两倍，就需要 D_KV = 640 × 2 = 1,280 GiB = 1.25 TiB。这里的 80 GiB 是另一个假设的单卡 KV 预算，不是某款 GPU 的总显存。机器总内存还要额外容纳系统、进程和索引等开销。

容量实验的结果应结合瓶颈判断，不同现象对应不同的改进方向：

  • 活跃请求不断换出又换回。 这说明 HBM 中需要同时保留的数据过多。增加 DRAM 虽然能存下更多数据，却未必降低等待时间。
  • Host 缓存常在复用前被淘汰。 这时增加 DRAM 才可能直接改善命中，让值得复用的数据保留得更久。
  • 命中已经很高，但加载队列越来越长。 应优先处理搬运带宽和调度，继续增加缓存容量未必能让请求更快。

判断某次缓存命中是否划算，可以先比较“省掉的 prefill 时间”和“查找、排队、加载、校验及通信干扰带来的时间”。保存策略还要考虑后续复用概率，因为写出去却再也不用的 KV 只产生了成本。只统计命中了多少个请求会掩盖这些差别，命中一个很短的前缀与省掉整段长提示词的计算，价值可能相差很大。

从资源约束推导保存、路由与调度策略

先让数据放在最符合其使用方式的位置

越频繁访问的数据，越值得放在靠近计算的位置。对于希望保持较低生成延迟的服务，可以从以下分工开始：

  • HBM 保留活跃 KV。 后续生成步骤会反复读取这些数据，留在本地显存可以减少重复搬运。
  • 本机 DRAM 接住临时换出和本机可复用的数据。 它提供额外容量，也便于之后沿本地路径恢复。
  • 远端 DRAM 支持跨实例复用。 多个推理实例可以访问共享历史 KV，代价是使用时要考虑网络搬运。

这不意味着每一份 KV 都必须在所有层保存副本。本地中转副本是否值得留下，要看它会不会再次命中，以及留下它能否减少后续网络搬运。如果只是远端读取一次就不再复用，直接写入 HBM 可能更合适。

路由请求时，也应该把命中位置与实例负载一起看。某个节点已有更多 KV，通常能减少重算，但如果它的网卡已经排了长队，另一处副本或者部分重算可能更快。缓存命中数量需要转化为预计完成时间，才能支持这个选择。

再决定哪些 KV 值得保存

保存时机决定了缓存何时能被复用，也决定了搬运压力集中在哪里。可以先比较两种安排：

  • 及时保存新生成的 KV。 后续请求可以更早复用，GPU 回收时尚未写出的数据也会减少。但如果大量数据以后不会被访问，及时写入就会持续占用 PCIe、网卡和 Host 空间。
  • 等请求结束或需要回收时再保存。 这样可以减少持续同步，但搬运会集中到这些时刻，可能增加回收时的等待。

无论选择哪种时机，如果要异步保存，都需要确保源 HBM 数据在复制完成前保持有效，否则只是把等待隐藏到了接口之后，并没有解决正确性问题。

因为增量保存只能避免重复写入，无法避免“写出去却再也不用”，我们还需要决定哪些前缀值得进入缓存。选择性保存可以综合考虑复用频率、重算成本和副本位置，决定是否保存、保存多长以及保存到哪里。这个策略需要用请求记录验证，以免过早丢掉之后频繁使用的数据。

为什么控制排队可能比提高峰值吞吐更重要

后台写回和前台生成如果共享网卡，持续提交大量后台工作可能让前台通信等得更久。此时，一味提高搬运并发，可能让独立测试里的 GB/s 更好看，却拖慢用户看到的输出速度。

值得优先控制的是每张网卡的在途字节量，也就是已经提交但尚未完成的数据总量。它比单纯的请求数更容易反映压力，因为一个 4 KiB 传输和一个 4 MiB 传输占用的工作量不同。可以根据前台延迟调整这个上限，并让阻塞新请求的加载优先于低价值的后台写回。

在这之前，还应该确认内存与设备的连接是否合理。例如，把源 Host 内存分配在靠近网卡的 NUMA 节点，可以避免不必要的跨 CPU 访问。对本地 KV 加载，应优先评估可行的 CUDA 本地复制，并在完整推理负载下确认它是否减少了共享资源争用。

按层预取和计算重叠可以作为后续优化，但它需要推理引擎参与，实施成本更高。优先记录真实搬运字节、排队和复用情况，先消除冗余与明显争用，再判断这类改动能为完整请求节省多少时间。

怎样验证这些设计在完整推理服务中的效果

为什么需要同时测搬运吞吐与前台延迟

搬运 KV 和生成 token 可能共用网卡、PCIe 连接或内存带宽。单独测试搬运时，提交更多任务往往有助于保持设备忙碌。但在完整服务中，同一批后台任务也可能让等待通信的前台计算更晚获得资源。因此，我们需要同时观察 KV 搬运量和用户可感知的延迟，才能判断优化是否有效。

这种依赖在多 GPU 推理中尤其明显。例如，MoE（Mixture of Experts，混合专家）模型会把不同输入分配给不同的专家子网络。专家分布在多张 GPU 上时，一步计算可能需要先分发数据，再收集结果。如果这些通信与 KV 搬运共享资源，额外等待就可能延长 token 的生成间隔。即使外部网口没有跑满，也应继续检查设备队列、PCIe 和 Host 内存等共享环节，不能只凭网口利用率排除争用。

验证时先建立没有后台 KV 搬运的推理基线，再在相同前台负载下加入搬运，同时观察几类指标：

  • KV 搬运吞吐： 每秒实际完成多少数据传输，判断搬运能力是否满足需求。
  • 首 token 延迟（TTFT）： 新请求要等多久才能开始输出，判断缓存加载是否拖慢了请求启动。
  • 连续 token 的输出间隔： 判断后台搬运是否干扰了正在生成的请求。
  • 满足服务目标的请求数： 判断吞吐增长是否真正转化成了可用的服务能力。

平均值容易掩盖少量很慢的请求，因此延迟指标还应观察 P99，即第 99 百分位，表示 99% 的观测值不超过它。具体采用哪个百分位，应与服务目标一致。

为什么用在途字节量控制积压，以及怎样选上限

只限制搬运任务数，无法准确表达设备面临的工作量，因为不同任务的数据大小可能不同。因此，我们用已经提交但尚未完成的总字节数，也就是在途字节量，限制后台同时占用的传输窗口。把窗口设得太小，可能因为任务补充不及时而浪费带宽。设得太大，则可能让更多后台工作积压，增加其他流量的等待。

为了找到合适的范围，可以先固定单次传输块大小和前台负载，从较小的窗口开始逐步增加，同时记录实际搬运吞吐、排队时间和前台延迟。这样先观察并发窗口的影响，再单独调整块大小，避免多个变量同时变化后无法解释结果。短时突发与持续搬运也应分别覆盖，因为相同的平均流量可能形成不同的排队压力。

如果某一段窗口范围内，继续增加在途字节量已经不能明显提高有效吞吐，却持续恶化前台延迟，就没有必要为了让设备队列更满而继续增加窗口。我们可以选择能够满足搬运需求且留有余量的较小窗口，并在前台延迟接近目标上限时减少后台提交。若必须立即加载 KV 才能推进请求，则应结合该请求的等待期限分配优先级，同时避免后台保存长期得不到服务。

这个方法给出的是选择参数的过程，不是某个固定的最佳字节数。网络往返时间、任务提交开销、数据方向和设备连接变化后，能够保持吞吐的窗口也会变化。使用设备提供的流量分类或优先级功能时，同样要验证实际效果，因为分类本身并不会增加共享资源的总容量。

怎样把测量结果归因到具体设计

完成基线和窗口实验后，再逐项改变影响路径、容量和排队的条件。下面的表格用于帮助定位瓶颈，不要求一次运行所有组合。

维度 需要回答的问题
搬运方向 Host DRAM→HBM 和 HBM→Host DRAM 是否有明显不对称？必要时再测 Host DRAM→Host DRAM 和 HBM→HBM。
数据位置 同机与跨机差多少？把 Host 内存放到网卡所在的 NUMA 节点后是否改善？
设备连接 每张 GPU 对应哪张网卡？多设备是否共用 PCIe 上行连接？CX-8 的两个 Ethernet 端口是否都被利用？
并发业务 单独搬运时很快，加入真实 decode 和多 GPU 通信后，最慢那部分请求是否明显变慢？
提交方式 改变块大小、提交批量和每网卡在途字节量，是否能保持吞吐并降低等待？
数据路径 远端 DRAM 直达 HBM、本机 DRAM 中转和可行的本地 DRAM→HBM CUDA 复制，各自在哪类请求上更合适？
缓存收益 实际命中了多少 KV 字节，省掉了多少 prefill，保存的数据后来有没有再次使用？
耗时构成 排队、实际传输、校验、同步分别花多久？数据真正可供 GPU 计算的时刻是什么？

测量时固定模型、上下文分布和前台并发，记录 GPU、网卡、驱动与固件版本，并通过重复运行观察结果是否稳定。除了 P99，也可以记录 P50 和 P99.9，它们分别表示中位数与第 99.9 百分位，帮助判断改善发生在普通请求还是极端慢请求上。还应分别记录传输完成、数据对 GPU 可见和计算消费数据的时刻，才能知道等待究竟发生在哪里。
