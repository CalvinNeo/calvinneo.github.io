学习 KVCache：硬件和架构

发表于 2026-09-11 |

设计 KVCache，不能只问“还有多少内存能用”。更关键的是，这些 KV 下一次在什么时候被谁使用，为了赶上那次计算，又必须经过哪些链路。

这和数据库的缓存设计有不少共通之处：缓存容量决定能留下多少工作集，I/O 带宽决定缺失的数据能多快补回来，调度则决定谁为这次补数等待。不同的是，LLM 在生成过程中会反复访问历史 KV，HBM 和外部链路的带宽差距又很大。因此，把数据放进更大的内存池，并不等于 GPU 就能把这部分内存当作本地显存使用。

下面沿着“KV 数据量 → 硬件路径 → 搬运预算 → 缓存和调度设计”展开。硬件峰值引用厂商规格，演算参数则明确标成假设，不把估算结果当作 benchmark。

先明确缓存的对象和访问方式

这里的 KV 是 Transformer attention 中的 Key 和 Value，不是存储系统里那个泛指键值映射的 KV。在每一层 attention 中，当前 token 的 Query（查询向量，简称 Q）与历史 token 的 K 计算匹配程度，再据此对 V 加权，得到需要从上下文中提取的信息。在标准因果 attention 中，追加 token 不会改变已有 token 的 K/V，所以可以保存这些中间结果，避免每生成一个 token 都把历史部分重新算一遍。

Prefill 是处理输入提示词、建立这些 KV 的阶段。Decode 是利用已有 KV 逐步生成后续 token 的阶段。对于本文默认讨论的 dense attention，也就是每一步都关注全部可见历史位置的注意力计算，缓存消除的是历史 K/V 的重复计算，并没有消除对它们的读取。这是后面所有带宽约束的起点。

从存储系统的角度看，KVCache 更像一份有明确计算上下文的物化中间结果。相同前缀在相同模型、位置编码等条件下可以复用，但它不是“相同文本片段就有相同内容”的普通对象缓存：同一句话出现在不同的前文之后，算出的 KV 通常也不同。

活跃 KV 通常放在 HBM（High Bandwidth Memory，高带宽内存） 中，让 GPU 在后续 decode 中反复读取。本文把 CPU 侧系统内存简称为 Host DRAM，以便区分两种位置。HBM 本身也是 DRAM 技术，这里不是在区分“是不是动态内存”。

先算一份 KV 有多大

KV 大小要从模型实际保存的张量推导，不能仅凭“模型有多少参数”估算。以 GQA（Grouped-Query Attention，分组查询注意力） 为例，多个 Q head 会共享一组 K/V head。这里的 head 是 attention 的一组向量通道，head_dim 是每个向量的元素数，所以应该按 KV head 数计算缓存，而不是按 Q head 数计算。

这样，后面出现的 4 GiB 就有了明确来源。为了观察长度和并发的影响，再选取 8,192 个 token 和 64 个请求两个示例输入：

示例工作负载 推导 全模型 KV 有效数据量

一个请求，32,768 个 token 128 KiB × 32,768 4 GiB
64 个请求，各有 32,768 个 token，没有共享前缀 4 GiB × 64 256 GiB

这些是逻辑数据量，还没算块内碎片、索引、预留空间以及并行布局中的复制。TP（Tensor Parallelism，张量并行）把同一层的计算拆到多张 GPU，PP（Pipeline Parallelism，流水线并行）把不同层分给不同 GPU。每张卡实际保存哪些层、哪些 KV head，应以推理引擎的布局为准，不能看到八张卡就直接把所有占用除以八。

这条公式也不是所有 attention 结构的通式。例如 MLA（Multi-head Latent Attention，多头潜在注意力）会缓存压缩的潜在表示，不能照搬完整 K/V 的尺寸。KV 量化会改变每元素占用，并可能引入缩放系数等辅助数据；仅仅量化模型权重，则不会自动缩小 KVCache。

区分“复用计算结果”和“扩展活跃工作集”

前缀缓存（prefix caching）保存的是未来请求可能复用的提示词前缀。命中后，可以少做相应的 prefill。这类似于复用一份物化结果：收益来自省掉计算，但如果结果在远端，还得先把它取回来。它通常首先改善 TTFT（Time To First Token，首 token 延迟），也就是请求发出到收到第一个输出 token 的时间，并不自动减少后续 dense decode 对历史 KV 的读取。vLLM 对前缀缓存收益范围的说明

Offload（卸载）则是把 KV 从 HBM 转移到 Host DRAM 或存储设备。这个词容易掩盖两种很不一样的行为：一种是暂停请求，用到时恢复一次，然后让它继续留在 HBM；另一种是 HBM 始终装不下整个活跃工作集，每个 decode 步骤都要从外部取数。前者主要付出恢复时延，后者会持续消耗链路带宽，性质更接近工作集超过内存后的反复换页。

因此，讨论“DRAM 能不能承接 KVCache”之前，应该先明确：是在保存历史计算结果，还是要让 DRAM 参与每一步生成。下面把两者放到同一套硬件预算中比较。

硬件数字，先对齐路径和口径

Host DRAM 和 SSD 没有在表里填一个“通用带宽”。前者要看内存通道、实际读写组合及 NUMA 位置，后者要看设备型号、数量和 I/O 模式。它们都可能成为路径上的瓶颈，不能因为没填数字，就在后面的估算中默认无限快。

为什么 PCIe 是 63 GB/s，而 HBM 不用除以二

PCIe 5.0 每条 lane 的单向速率是 32 GT/s，这是 PCIe 规范使用的物理层速率单位。G 是十亿，T 是 transfer，合起来表示每秒 32 × 10^9 次传输。这里的 transfer 不是一次内存读写事务，更不是一个数据包。Gen5 使用 NRZ（Non-Return-to-Zero，不归零）二电平信号，每次传输携带 1 bit，因此这里的 32 GT/s 对应 32 Gb/s 的原始比特率，尚未扣除线路编码和协议开销。

这与内存规格用 MT/s 而不是直接用 GB/s 的思路类似：先报告接口的传输速率，再结合每次携带的数据量、并行宽度和编码效率，换算成带宽。PCIe 的 ×16 表示 16 条 lane，而 128b/130b 编码表示每传输 128 bit 内容需要占用 130 bit 链路空间，于是：

这还不是应用吞吐，因为 PCIe 的 TLP（Transaction Layer Packet，事务层数据包）还要携带地址、操作类型等信息。Gen6 的链路编码不同，不能继续照搬 128/130。它采用固定大小的 FLIT（流控单元）打包，并引入 FEC（前向纠错），用冗余信息修正部分传输错误。因此，表中的 128 GB/s 是原始带宽，不是扣完开销后的 KV 搬运能力。PCI-SIG 的 FLIT 与 FEC 说明

HBM 的口径又不同。B200 的 8 TB/s 表示所有 HBM 通道合计的峰值传输能力，纯读理论上可以使用这份总带宽，不需要因为存在读写两种方向就先除以二。混合读写时，它们争用内存通道，当然也不能理解为“同时读 8 TB/s、写 8 TB/s”。

最有用的比较不是哪张规格表上的数字更大，而是数据在哪里。8 TB/s = 8,000 GB/s，与 Gen5 ×16 的 63 GB/s 相比，峰值相差约 8,000 / 63 ≈ 127 倍。这不是一次 KV 加载的加速比，而是在提醒我们：反复从外部读取的代价，与把数据放进 HBM 后反复读取，不在同一个量级。

GPUDirect RDMA 省掉了哪一段

RDMA（Remote Direct Memory Access，远程直接内存访问）让网卡直接访问事先注册并授权的内存。注册的作用是建立地址映射和访问权限，不是再复制一份数据。GPUDirect RDMA进一步让第三方设备访问 GPU 显存，使接收端网卡可以把数据直接写入 GPU，而不必先落到 Host DRAM。

CUDA 是 NVIDIA 的 GPU 编程与运行时平台，本地 Host↔GPU 复制可以通过它发起。这里列的是候选路径，不是在断言某个 KVCache 系统一定采用其中一种实现。

GDR（下文对 GPUDirect RDMA 的简称）省掉的是接收端 Host 中转，没有省掉源端取数、网络传输和 GPU 接入链路。这和存储系统的 zero-copy 优化一样：少一次中转可以少占资源，但不意味着数据无需经过总线，也不保证任意拓扑下都更快。

拓扑尤其需要单独核对。如果网卡和 GPU 位于支持设备间转发的同一个 PCIe switch 下，数据可能不必绕到 Host 内存一侧。如果路径跨 CPU socket，则还可能受到跨 NUMA 互连、平台支持和设备间访问限制的影响。多张卡共用的上行链路也不能重复计入总带宽。NVIDIA 对 GDR 路径和拓扑的说明

CX-8 为什么不等于“恢复时间直接减半”

从 CX-7 的 400G 升到 CX-8 的 800G，增加的是网络一段的能力。要把它转化为端到端吞吐，端口、网卡的主机接口和 GPU 的接入路径都必须跟得上。

首先，800G 不一定是一个 Ethernet 端口。官方列出的 CX-8 C8180 支持单端口 800G XDR InfiniBand，其中 XDR 是 InfiniBand 的速率代际名称。它的 Ethernet 模式可以是两个 400GbE 端口，C8240 的默认模式也是 2×400GbE。InfiniBand 与 Ethernet 是不同的网络体系，不能混用端口配置结论。在上述 Ethernet 模式下，100 GB/s 是两端口单向能力的合计，软件必须实际分散传输，不能指望只用一个端口就达到整卡速率。CX-8 端口配置

其次，CX-8 支持 PCIe 6.0 ×16，但插到一条 Gen5 ×16 上，经过这条连接的数据仍受约 63 GB/s 的单向理论上限约束。适用的 Socket Direct 型号可以借助辅助卡和线缆接入两条 Gen5 ×16，聚合主机 I/O 能力。这是一种需要对应型号、插槽和拓扑配合的接入方式，不是所有 CX-8 都会自动获得两条链路。CX-8 的主机接口与 Socket Direct 说明

最后，即使网卡侧已经有足够带宽，目标若是只有一条 Gen5 ×16 接入路径的 GPU，这个请求仍会受 GPU 端限制。多个 GPU 分担数据才有机会使用更高的网卡总带宽，而且还要确认它们没有汇聚到更窄的共享链路。升级能快多少，取决于原来的瓶颈在哪，以及升级后瓶颈转移到了哪里。

第二行中，本地路径可以并行，因此时间仍是 4 GiB / 50 GB/s。但远端加载要让一张网卡搬完全部 32 GiB，于是变成 32 × 2^30 / (40 × 10^9) ≈ 859.0 ms。整批中转还得再加 85.9 ms，得到 944.9 ms。瓶颈不是“远端内存天生慢十倍”，而是数据量增加了八倍，网络总带宽却没增加。

第三行把独立网络路径也增加到八条，总有效带宽变成 8 × 40 = 320 GB/s，所以 32 GiB / 320 GB/s ≈ 107.4 ms。它要求源端与目标端都能提供相应的并行能力，而不只是目标机器上有八张网卡。

流水化可以隐藏时间，但不能消除工作量

单 GPU 算例中，网络需要 107.4 ms，Host→GPU 复制需要 85.9 ms。由于复制比网络快，充分流水化的 Host 中转也可能接近 107.4 ms。因此，不能拿串行中转的 193.3 ms 与直达的 107.4 ms 比较，就断言 GDR 必然带来接近两倍的加速。

那么，既然可以重叠，为什么还希望绕过 Host？因为重叠减少关键路径上的等待，绕过中转减少系统实际要做的工作。两者优化的对象不同。

以接收端为边界，按有效载荷记账，两种路径处理同一份 4 GiB KV 时需要完成：

接收端工作 直达 HBM Host 中转，含流水化实现
从网络接收 KV 4 GiB 4 GiB
向 Host 内存写入中转数据 0 4 GiB
从 Host 内存读出中转数据 0 4 GiB
最终写入 HBM 4 GiB 4 GiB

Host 中转额外产生 4 + 4 = 8 GiB 的内存读写需求。这是累计流量，不是必须分配 8 GiB 缓冲区，循环复用较小的缓冲区就可以完成流水线。它也不是对物理 DRAM 总线流量的精确测量，因为平台缓存和 I/O 实现可能改变实际访问。表中的 0 仅表示不再中转这份 KV，控制面和元数据仍会使用 Host 内存。

如果持续以 40 GB/s 接收，中转路径就要承接约 40 GB/s 的 Host 写入和 40 GB/s 的 Host 读取，合计 80 GB/s。多路并发会继续叠加这些需求，一旦内存控制器或跨 NUMA 路径出现争用，独立测试中“复制能完全追上网络”的前提就可能失效。单请求耗时相近，不代表两种方案的并发余量相同。这与把一次额外内存复制藏进异步 I/O 相同：调用者不再同步等待，不代表内存带宽成本消失了。

中转还需要完成一次“收到块 → 发起复制 → 确认 GPU 可使用 → 复用缓冲区”的交接。复制通常由 DMA 硬件完成，CPU 不需要逐字节搬运，但提交、完成通知和生命周期管理仍在。至于能少占多少 PCIe 带宽，要看数据实际经过哪些共享链路，不能概括成“GDR 让所有 PCIe 流量减半”。

这并不意味着 Host 中转总该删除。如果 HBM 尚未腾出空间，它可以接住提前预取的数据；如果同一前缀稍后还会在本机复用，它又顺便完成了本地缓存填充。需要 CPU 处理数据，或平台不适合 GDR 时，中转也有实际价值。应该删除的是没有后续用途的中转工作，而不是为了追求某个 zero-copy 标签，删除真正有用的缓存层。

分层缓存：先分清职责，再设计接口

每一层保存什么，取决于下一次访问

有了搬运预算，分层就不只是把存储设备按快慢排个序。真正决定放置位置的是访问方式：活跃 KV 会在后续 decode 中反复读取，历史前缀只是可能被未来请求复用，而暂停请求的 KV 则关系到它什么时候能恢复执行。

位置或路径 适合承担的职责 主要约束
HBM 保存活跃 KV，服务后续反复读取。 受单卡可用容量限制，要与权重、激活和算子工作区共同预算。
本机 Host DRAM 保存本机可能复用的前缀，接住临时换出和提前预取。 恢复仍需经过 GPU 接入路径，还要考虑 NUMA 位置和内存读写竞争。
远端 DRAM 在多个推理实例之间共享历史 KV。 命中不等于立即可用，恢复需要消耗网络带宽并承担排队。
NVMe SSD 以较低的单位容量成本保留更冷的历史 KV。 NVMe 是访问 SSD 的协议，具体读取能力仍取决于设备和 I/O 模式，恢复预算要计入这一段。
Prefill GPU→Decode GPU 让不同 GPU 分别执行输入处理与后续生成，并交接 KV。 源端必须保留数据直到交接完成，跨节点交接还会占用网络。

最后一种叫 P/D 分离，它分离的是 prefill 和 decode 两个推理阶段，不是前面 PP 那种按模型层划分的流水线并行。P/D 交接也不天然需要一个长期缓存层，直接把 KV 交给 Decode GPU 就可以完成这次交接。

这些方案可以组合，但不需要让每份 KV 都在每一层留下副本。例如，接收端只会使用一次的远端 KV，可以直接写入 HBM；如果本机还会反复复用它，保留 Host 副本才有额外价值。SGLang 的 HiCache将 GPU、Host 内存与共享存储组织成分层缓存，Mooncake 则把共享 KV 与推理调度结合起来。它们提供了实现参考，但收益仍取决于各自的请求复用模式与硬件路径。HiCache 设计文档

保存历史前缀与临时换出，不是同一种提交语义

两种操作都可能把 KV 从 HBM 复制到 DRAM，但需要保证的事情不同。

保存历史前缀，是为未来请求保留一份可复用的计算结果。这份数据是可重算的派生状态，不是数据库里必须持久化才能确认事务成功的日志。保存失败时，可以放弃这次缓存机会，让未来请求重新 prefill。为了找到可复用的数据，需要维护从前缀及其计算条件到缓存块的索引，但只有目标数据已经可用，才能把索引条目发布为可命中。

临时换出，是为了给仍未结束的请求腾出 HBM。如果调度器承诺之后从这份 KV 恢复，就必须在回收源块之前确认有可用的目标副本。换出失败时，要么保留源数据，要么明确转入重算，不能一边释放唯一副本，一边仍把请求记成“可以直接恢复”。

因此，保存完成、发布缓存、回收源块，是不同的事件。异步复制成功并不意味着 HBM 块可以立即回收，因为计算或者其他共享该块的请求可能还在使用它。同样，从 Host 恢复到 HBM 后，也不意味着 Host 副本应该立即删除，它可能还服务其他请求。这个问题与异步 I/O 中缓冲区的引用计数很接近：I/O 持有的引用只是其中一种，完成 I/O 不代表所有读者都已退出。

前缀索引不能只对当前块的文本做 hash

标准因果 attention 中，一段 token 的 KV 依赖它之前的上下文。即使两个块包含相同的 token，只要前缀不同，也不能直接认为 KV 相同。因此，缓存身份至少要覆盖完整前缀关系，以及模型权重版本、位置和 attention 配置等影响计算结果的条件。实现上可以把父前缀身份和当前 token 块一起纳入索引键，而不是只对当前块独立取 hash。

找到数学上可复用的 KV 后，还要检查物理表示是否兼容，包括 KV 精度、张量布局和并行分片方式。如果两侧表示不同，就可能需要转换或重分片，不能把“缓存命中”直接等同于“可以原样复制”。跨租户共享还应满足访问隔离要求，不能仅因为内容 hash 相同就默认允许复用。

分配与回收通常以缓存块为单位，一个块容纳一组 token 的 KV。已填满且发布的块可以保持不变，便于多个请求共享；尚在追加的尾块则需要避免被共享者看到不完整的内容。共享尾块需要继续写入时，可以采用写时复制，也就是先建立独立副本，再修改，而不是改动所有请求正在共享的物理块。

块大小会同时影响索引数量、未填满空间和可复用的前缀粒度，但它不必等于网络传输块大小。前者是缓存管理单位，后者是 I/O 提交单位，而按层预取又有自己的计算就绪粒度。把这三个概念绑成一个大小，常常会让分配、带宽和流水线目标互相牵制。

对于历史缓存，可以像分析数据库 block cache 一样，回放请求轨迹，观察按字节计量的工作集和复用距离，也就是两次访问之间经过了多少不同的 KV 数据。然后比较不同容量下能保住多少有价值的前缀，以及这些命中到底省下多少 prefill。这样得到的是容量—收益关系，而不是从 GPU 型号猜一个比例。

这也是为什么没有通用的最佳比例。如果 Host 中的数据经常在复用前被淘汰，增大 DRAM 可能有效；如果 HBM 因活跃工作集过大而反复换入换出，增大 DRAM 只是提供更大的换出空间；如果命中率已经很高，恢复队列却持续增长，首先要解决的是搬运能力和调度。三个现象需要三种不同的处理方式。

保存、路由与背压，都应围绕完成时间

缓存命中不是最终目标

一次命中是否划算，要比较它省掉的 prefill 与新增的查找、排队、加载和同步。对于“整份加载后再计算”的简单实现，可以分别估计缓存路径和重算路径的首 token 时间。若支持分块计算重叠，就应改为分析实际依赖图上的关键路径，不能把所有时间机械相加。

请求路由也应使用这个判断。缓存命中最多的节点未必最快，因为它可能已经排着很长的恢复队列；前缀命中稍少但负载更低的节点，甚至直接重算，都可能更早输出。类似于带缓存局部性的数据库路由，局部性是输入条件，而不是必须坚持的绑定关系。

保存策略则要考虑未来价值。新块生成后及时保存，可以更早服务后续请求，也能减少回收 HBM 时尚待写出的数据，但会持续占用链路。等请求结束或确实需要换出时再保存，可以延后甚至避免部分写入，却可能把搬运集中到请求结束或显存紧张的时刻。无论什么时候保存，异步任务都必须持有源块，不能让“接口很快返回”掩盖源数据已被回收的问题。

因此，应结合复用频率、前缀长度、重算成本和已有副本位置，决定是否进入缓存、保存到哪一层。不能只看请求命中率，因为命中很短的一段前缀，与省掉整段长提示词的计算，价值并不相同。更直接的指标是命中的 KV 字节、节省的 prefill，以及保存后真正被再次使用的数据比例。

在途窗口要填满链路，但不要拿前台延迟换跑分

KV 搬运与多 GPU 推理可能共享网卡、PCIe 或内存带宽。例如 MoE（Mixture of Experts，混合专家）模型会把 token 路由到不同专家子网络，专家分布在不同 GPU 时，需要传递输入并汇集结果。如果这些通信与 KV 搬运使用同一组资源，后台写回即使提高了自身 GB/s，也可能拉长正在生成的请求的 ITL。

可以用每张网卡的在途字节量控制已提交但尚未完成的搬运工作。它比只限制任务数更能反映数据压力，因为传输大小可能相差很大。但字节上限也不能替代操作数上限，大量小任务仍可能耗尽提交和完成处理能力。

在固定块大小、尚未出现明显排队时，如果目标吞吐是 B，一次提交到完成的平均时间是 L，保持链路忙碌所需的在途窗口大致在 B × L 这个数量级。推导很直接：等待完成的这段时间里，要有足够的字节持续供设备处理。它类似网络的带宽时延积，但这里的 L 包含实际 I/O 路径的完成周期，不应只拿裸网络 RTT 代替。

这个估计只是起点。固定块大小和前台负载，逐步增加窗口，观察有效吞吐何时不再提升、前台尾延迟何时开始恶化。窗口过小会让设备断粮，过大则只是把更多后台工作堆进队列。已经处于拥塞状态时，更不能拿被排队拉长的完成时间继续推高窗口。

优先级也应按依赖关系决定。阻塞新请求的恢复通常比低复用价值的历史保存更急，但为了释放 HBM 而进行的必要换出同样可能阻塞前台，不能把所有写回一律降为最低优先级。降低后台提交量能减少干扰，但不能代替正确的 NUMA 放置和设备拓扑，也不能凭软件优先级创造额外带宽。

验证：把搬运性能和推理收益放在一起看

先用单路径测试确定传输能力，再在真实推理负载中验证收益。这两个阶段回答不同的问题：前者说明硬件路径能搬多快，后者说明在当前请求分布和资源竞争下，搬运是否值得。

单路径测试应分别覆盖本地 Host→HBM、远端直达 HBM 和 Host 中转，并单独测反向换出。记录数据大小、并发、内存注册是否已完成，以及两端的 NUMA/PCIe 位置。冷启动的连接与注册成本应单独报告，不要有时算进去、有时又排除。

完整服务则使用相同的模型、请求内容、到达序列和并发限制进行对照。分析后台搬运干扰时，先建立没有这类后台工作的前台基线，再加入保存或恢复任务。评估缓存收益时，还应对照命中后加载与直接重算两条路径，而不只是比较搬运吞吐。

满足 SLO 的请求数 更高的设备利用率是否真的转化成可用的服务能力？
排队时间与在途字节量 时间消耗在传输本身，还是因为提交过量而等待？
Host 读写、NUMA 与共享链路压力 流水化是否只是隐藏了等待，中转工作是否仍在制造争用？
缓存命中字节、复用次数与节省的 prefill 新增容量保存的是有价值的工作集，还是再也不会读取的数据？

归因时一次只改一个主要变量，例如先固定块大小调整窗口，再固定窗口比较路径。也要分别测试短时突发和持续流量，相同平均带宽不代表相同排队压力。网口没跑满不能直接排除通信瓶颈，设备队列、共享 PCIe、Host 内存或者 GPU 同步都可能先成为限制。

最后，把“任务入队、传输提交、后端完成、数据对 GPU 可用、计算开始”分别记录下来。这样才能区分索引慢、排队长、链路慢与同步等待，而不是看到一个总耗时就继续堆网卡或调并发。GPU、网卡、驱动和固件版本也要随结果保留，避免把平台差异误认为算法收益。

回到最初的问题：设计 KVCache 不是把 GPU 缺的容量接到更大的内存池上，而是安排一份计算结果何时产生、在哪里保留、何时迁移，以及谁为迁移等待。活跃数据的重复访问决定 HBM 的价值，历史数据的复用决定 DRAM/SSD 的价值，二者之间的字节预算和就绪语义，才决定这套分层能不能真正服务推理。
