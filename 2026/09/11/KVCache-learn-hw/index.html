学习 KVCache：硬件和架构

发表于 2026-09-11 |

这篇笔记想弄清楚两个问题：把历史 KV 放进更大的内存池，究竟是在节省计算，还是在扩展 GPU 的活跃工作集？一份 KV 即使命中了缓存，把它恢复到能继续计算的状态，又要付出多少代价？

我更愿意从“复用一份计算状态”来理解 KVCache，而不是从“增加一层缓存”开始。它类似于数据库中的物化中间结果：保留下来能省掉一部分计算，但结果不在执行端时，还要把它取回来。大语言模型在生成过程中又会反复读取历史状态，这就让“恢复一次”和“每一步都从外部读取”成了两笔性质不同的账。

下面用一份 4 GiB 的 KV 串起这些问题，这个大小会从模型参数推出来。全文的主线是：先辨认正在复用什么状态，再沿实际路径计算搬运成本，最后看它是否减少了请求的等待。文中的产品参数来自公开资料，计算使用的工作负载与有效带宽则是明确设定的算例，不是实测成绩。

KVCache 保存的状态与复用边界

这里的 KV 是 Transformer 注意力计算（attention）中的 Key 和 Value，不是泛指键值映射。文本经过分词器编码后成为 token 序列，token 是模型处理的离散单位，不与汉字或单词一一对应。在每层 attention 中，模型从各位置的输入表示生成 Query、Key 和 Value 向量，简称 Q、K、V。当前位置的 Q 与可见位置的 K 计算相关性，得到归一化权重，再用这些权重对 V 加权求和。

本文讨论的因果自注意力（causal self-attention），只允许一个位置使用自身及此前位置的信息。“因果”这个限制，正是历史 KV 能保留的原因：后面追加一个 token，不会进入已有位置的可见范围，也就不需要改变那些位置已经算出的状态。保持模型和输入条件不变，就能保存各层的 K/V，供后续计算继续使用。

Prefill 是处理本轮输入、建立对应 KV 的计算阶段。Decode 则利用已有状态逐步生成后续 token。本文默认采用稠密注意力（dense attention），即每个查询位置都关注其因果范围内的全部位置。在这个假设下，缓存消除的是历史 K/V 的重复计算，没有消除新位置对历史 K/V 的读取。这是后面带宽分析的起点。

因此，一份 KV 的身份不只由它对应的文字决定，还取决于这段文字之前的上下文。多层 Transformer 的后续层使用已经融合前文信息的表示，同一段 token 接在不同前缀后面，不能视为同一份完整 KV。位置处理也属于计算条件，模型用它表示 token 在序列中的顺序，改变位置或位置编码方式同样会影响复用边界。

后面的算例以活跃 KV 驻留 GPU 显存为基准。文中涉及的 GPU 使用 HBM（High Bandwidth Memory，高带宽内存），它是一种以堆叠 DRAM 和宽接口提供高带宽的内存技术。CPU 侧系统内存则记作 Host DRAM。这个区分说的是数据位置，HBM 本身也属于 DRAM。

这段对话还藏着一个容易忽略的边界。在逐 token 的自回归生成中，模型先处理已有输入，产生下一 token 的分数，再从中选出一个 token。这个刚选出的 token 要作为下一步输入，才会建立自己的 K/V。如果生成恰好在选出它后结束，就不能把“已经输出”当作“已有 KV”。缓存按块发布时，还有完整块的边界。这里的缓存块是容纳一组连续 token 状态的管理单位，未发布的尾部不计入可复用范围。

反过来，即使输入的 KV 全部存在，也不等于能直接给出下一 token。KV 保存的是各层注意力所需的中间状态，不包含最终输出层的 logits，也就是各候选 token 在归一化成概率之前的分数。以截至 2026-10-15 查阅到的 vLLM 公开实现为例，它会为取得 logits 重算输入的末尾 token。如果输入长度恰好按块对齐，而该路径只接受完整块命中，就要回退最后一个块。这是该实现的消费边界，不是所有缓存都必须采用的策略。

所以，能够跳过多少计算，要看有效状态的边界以及引擎怎样消费它，不能拿已输出的文本长度直接代替。跨请求复用还多了一段生命周期：请求结束后保留状态，下次找到它，并在不位于目标 GPU 时完成加载。加载就位以后，decode 反复读取的是本地状态，不是每生成一个 token 都从远端重传同一份前缀。

一份 KV 有多大

KV 大小要从实际保存的张量推导，而不是从模型参数量估算。Attention head 是一组分别计算注意力权重和加权结果的向量通道，head_dim 表示该 head 中 Q/K 等向量的维度。以 GQA（Grouped-Query Attention，分组查询注意力）为例，Q head 被分组，同组的多个 Q head 共享一个 K head 和一个 V head。因此，缓存按 KV head 数计量，不按 Q head 数计量。GQA 论文

这些是全模型 KV 的逻辑载荷，未计入块内碎片、索引、预留空间和并行布局中的复制。TP（Tensor Parallelism，张量并行）拆分同一层的张量与计算，PP（Pipeline Parallelism，流水线并行）则把不同模型层放在不同阶段。前者影响每个 GPU 持有哪些 head 或分片，后者影响它持有哪些层。只有确认数据没有额外复制、各分片又足够均衡，才能把总量按 GPU 数平均。

这条公式的边界在于“保存完整 K/V”。例如 MLA（Multi-head Latent Attention，多头潜在注意力）通过低秩投影把 K/V 信息压入较低维的潜在向量，而不是缓存每个 head 展开后的完整 K/V。DeepSeek-V2 的公开定义还缓存一份用于位置计算的独立 Key 分量，因此连“只数一个压缩向量”也不够，仍要列出实际保存的全部张量。DeepSeek-V2 论文中的 MLA 定义

KV 量化又是另一种缩减。它用更少的位数表示元素，使用缩放系数的方案还要保存这些辅助数据。这里改变的是 KV 表示，仅量化模型权重不会自动缩小 KVCache。vLLM 的量化 KVCache 说明

区分“复用计算结果”和“扩展活跃工作集”

前缀缓存（prefix caching）保留已经算好的前缀状态，供后续请求跳过相应的 prefill。它直接省掉的是输入计算，收益主要体现在 TTFT（Time To First Token，首 token 延迟），也就是请求发出到收到第一个输出 token 的时间。这个收益还要扣除查找和加载的代价，而后续 dense decode 仍然需要读取历史 KV。vLLM 对前缀缓存收益范围的说明

Offload（卸载）则是把 KV 从 HBM 转移到 Host DRAM 或存储设备。暂停请求、之后恢复一次并继续驻留 HBM，是一种用法。HBM 始终装不下整个活跃工作集、每一步都从外部取数，是另一种用法。前者主要付出恢复时延，后者会持续占用链路，类似于工作集超过内存后的反复换页。

这就是“DRAM 能不能承接 KVCache”需要拆开的地方。保存历史结果，付出的是复用时的恢复成本。把装不进 HBM 的活跃状态长期留在外部，则让外部链路进入每一步生成的关键路径。两者使用相同的 KV 数据，却不能用同一种带宽预算评价。

HBM、PCIe 与网络是不同的数据路径

历史 KV 不在目标 GPU 上时，问题就从“省掉多少计算”变成了“沿哪条路径把状态搬回来”。这里讨论 GPU、Host 和网卡通过 PCIe 连接的服务器，其他 CPU–GPU 互连需要另算。为避免容量与带宽混用进制，下面统一用十进制 GB/s、TB/s 表示带宽，软件容量用二进制 GiB、MiB、KiB，分别对应 2^30、2^20、2^10 byte。网卡的 Gb/s 按 bit 计量，换成 GB/s 要除以 8。

HBM 在 GPU 封装里，但不是片上缓存

HBM 与 GPU 计算单元之间的距离很近，但它不是 GPU 裸片上的缓存。一个 HBM 堆叠由多片 DRAM 裸片（die）垂直叠放而成，裸片指封装前的单块半导体芯片。在 B200/B300 这类产品中，HBM 堆叠与 GPU 计算裸片同处一个封装，通过高密度互连连接。中介层（interposer）是这种封装中用于芯片间高密度布线的结构之一。Micron 对 HBM 结构的介绍

规格里的“单 GPU 合计带宽”是同一个 GPU 的各个 HBM 内存通道之和。通道内的读写共享数据线，不同通道则能并行调度，因此 7.7 TB/s 不是“同时读 7.7、再写 7.7”，也没有预先分成固定的读写份额。纯读可以利用这份总带宽，混合读写则要共同分配它，并承担方向切换等开销。这里相加的是并行通道的能力，不是把 HBM、PCIe 和 GPU 间互连这些不同路径的带宽相加。

PCIe lane 是相邻两个 PCIe 端口之间的一条全双工串行物理通路，由一对发送差分信号线和一对接收差分信号线组成。差分信号利用一对线之间的电压差表示信号，两对共四根数据信号线合起来才是一条 lane，如图 2 所示。

图 2：一条 lane 的物理组成。TX、RX 分别表示发送与接收，加减号标识差分对的两根信号线。

图中没有画参考时钟和地线。PCIe 链路由一条或多条 lane 组成，×16 表示这条链路使用 16 条 lane，Gen5/Gen6 表示代际，两者回答的是不同问题。器件一共有多少 lane，也不能代替某一段链路的宽度：两条 ×16 连接不是一条 ×32。数据在 lane 之间的分配由 PCIe 硬件完成，应用不会为某块 KV 指定“走第几条 lane”。PCIe 物理层与链路宽度概述

图 3：×16 链路的结构示意，不代表所有机型的实际协商宽度。每条细线表示一条完整的双向 lane，不是单根导线。

PCIe 5.0 每条 lane 的单向速率是 32 GT/s，这是规范标注物理层传输速率的单位，G 表示十亿，T 是 transfer。Gen5 使用 NRZ（Non-Return-to-Zero，不归零）二电平信号，一个符号表示 1 bit。它每秒发送 320 亿个符号，因此这时的符号率 32 Gbaud、规范标注的 32 GT/s 和原始比特率 32 Gb/s，在数值上恰好相同。Gbaud 计量每秒发送多少个符号，每个符号承载几 bit，则由信号编码决定。

到了 Gen6，变化集中在信号传输和数据组织两个方面：

  1. PAM4 让每个符号携带更多 bit。 PAM4（四电平脉冲幅度调制）用四种电平状态表示 00、01、10、11 这四种取值，因此一个符号能携带 log₂4 = 2 bit。Gen6 的符号率仍为 32 Gbaud，但每个符号携带的信息翻倍，单 lane 单向原始比特率就成为 32 × 2 = 64 Gb/s，规范将这一代的速率标为 64 GT/s。沿着“符号率→比特率→字节带宽”换算，×16 链路得到 32 × 2 × 16 ÷ 8 = 128 GB/s 的单向原始带宽，双向合计为 256 GB/s。这里的翻倍来自每个符号承载的信息增加，计算已经使用 64 Gb/s 时，PAM4 的这份收益就已经包含在内。CX-8 手册中的 PCIe Gen6 速率

  2. FLIT 与 FEC 改变了数据组织和纠错方式。 TLP（Transaction Layer Packet，事务层数据包）承载设备的读写请求及返回数据，包中既有载荷，也有地址、操作类型等协议字段。Gen6 用固定长度的 FLIT（Flow Control Unit，流控单元）组织这些信息，并加入 FEC（Forward Error Correction，前向纠错）冗余来修正传输错误。因而，刚才算出的 128 GB/s 要由载荷、协议字段和纠错信息共同使用，应用实际搬运 KV 的速度还要扣除这些开销。Gen5 的 128/130 对应另一套线路编码，Gen6 的载荷效率需要按其 FLIT 格式和实际事务组合计算。PCI-SIG 的 FLIT、PAM4 和 FEC 说明

现在把同一份 4 GiB 放在这两条路径上计算。如果数据完整经过本地 HBM 接口，按 7.7 TB/s，纯读的理想时间约为 4 × 2^30 / (7.7 × 10^12) ≈ 0.558 ms。从 Host 经过 Gen5 ×16 搬入，单是 PCIe 的理论时间就约为 4 × 2^30 / (63 × 10^9) ≈ 68.2 ms，按取整后的带宽相除约差 7,700 / 63 ≈ 122 倍。这个差值不是一次 attention 的加速比，它只说明跨过 PCIe 边界以后，同样的字节量进入了另一档时间预算。

GPUDirect RDMA 省掉了哪一段

RDMA（Remote Direct Memory Access，远程直接内存访问）允许适配器访问注册并授权的内存区域。以单边 RDMA Write 为例，发起方提交远端地址与访问凭据，接收端不需要由 CPU 逐字节接收、再复制这份载荷。注册建立的是设备可使用的地址映射和权限，并不是制作数据副本。GPUDirect RDMA把这类设备访问扩展到 GPU 显存，让接收网卡直接写入 GPU，而不必先落到 Host DRAM。

这条路径也由设备的连接方式决定。PCIe 交换器（PCIe switch）是连接多个 PCIe 端口、按地址和路由转发事务包的硬件，类似网络交换机承担的转发角色，但这里处理的是 PCIe 事务。网卡与 GPU 接在同一个交换器下，而且平台允许设备间对等转发时，事务可以直接在交换器内到达 GPU，省去 Host 中转。跨 CPU socket 的设备访问则还要经过 CPU 间互连，并满足平台的对等访问支持。判断 GDR 路径时，需要沿设备之间经过的连接来分析。NVIDIA 对 GDR 路径和拓扑的说明

CX-8 的端口模式与 PCIe 接入带宽

CX-8 的 800 Gb/s 描述网络侧的总速率。一次 KV 搬运能用到多少，还取决于这些速率分布在哪些端口，以及载荷经过怎样的 PCIe 连接。把网络入口和设备接入放到一起，才能解释整卡带宽如何变成一次加载的带宽。

800G 首先要落实到端口模式。InfiniBand 是面向高性能互连的网络体系，与 Ethernet 不是同一套链路协议，XDR 是其中的速率代际。官方列出的 CX-8 C8180 支持单端口 800G XDR InfiniBand，其 Ethernet 模式则支持两个 400GbE 端口，C8240 的默认模式也是 2×400GbE。在这些 Ethernet 模式下，2 × 400 ÷ 8 = 100 GB/s 是两端口的单向合计，单独使用一个端口只能对应其中一半。CX-8 端口配置

PCIe 一侧，CX-8 支持 Gen6 ×16。若实际连接为 Gen5 ×16，经过这段连接的载荷就受前面算出的约 63 GB/s 单向上限约束。假设网络与一条 Gen5 ×16 恰好串在同一次搬运路径上，仅比较这两段的理论能力，就是 min(100, 63) = 63 GB/s。若两端都以 Gen6 ×16 接入，PCIe 的单向原始上限提高到 128 GB/s，才有条件承接 100 GB/s 的网络载荷，实际吞吐再由内存、协议开销和共享资源决定。

目标 GPU 的接入也按同样方法核算。一份数据最终进入一张 GPU，就要经过那张 GPU 的接口。分到多个 GPU 时，每路独立的连接能够分担载荷，共用的上行则仍只提供一份带宽。这与网卡有几个端口一起，决定了整机并发传输能使用多少资源。

根端口是主机侧 PCIe 层次结构的起点。从 CPU 向下读图，先到交换器朝向主机的上游端口，再由朝向 GPU 的下游端口接出。CPU→CX-8 这一段是 Gen5，CX-8→GPU 这一段是 Gen6，两段分别建立链路、协商速率和宽度。

Host 向本机 GPU 搬 KV 时，事务经过 CX-8 的 PCIe 交换部分，不必进入网络收发分支，更不需要封装成以太网流量绕一圈。这里的“经过交换部分”描述的是 PCIe 事务如何从 Host 侧端口路由到 GPU 侧端口，并不等于使用 GDR：源数据在 Host DRAM，目标是 GPU HBM，属于 Host→GPU 的本地复制。GDR 的边界是网卡等第三方 PCIe 设备直接访问 GPU 内存，所以远端网卡把 KV 直接写入目标 GPU HBM 时，才是本文所说的 GDR。若远端数据先经 RDMA 写入本机 Host DRAM，再由本机复制到 GPU，后半段仍是 Host→GPU 的本地复制。

网络数据直达 GPU 时，则由 CX-8 的网络收发功能接收数据，再通过它的 PCIe 交换部分送到 GPU，不必先落到 Host DRAM。这条“网卡→GPU”的数据面路径才对应前面介绍的 GPUDirect RDMA。于是，同一个器件可以出现在两条路径上，但 Host→GPU 复制和网卡→GPU 直达使用的功能分支、发起方和带宽约束并不相同。

因此，计算本机 Host→GPU 的搬运能力，要同时列出 Gen5 和 Gen6 两段，再找其中的限制。计算远端直达，则沿“源端内存→源端网卡→网络→目标 CX-8→目标 GPU”展开，目标 CPU 的 Gen5 链路不在这条载荷路径上，源端的内存和 PCIe 却仍然在。这是按路径预算带宽的具体做法。

NVLink 是 GPU 等处理器之间的高速互连，NVSwitch 是连接这些链路的交换器。它们与这里的 PCIe 交换器不是一回事。KV 若直接到达负责消费的 GPU，加载无需再绕 NVSwitch。若采用另一张 GPU 转发，才需要计入那段 GPU 间传输。带宽预算要按实际经过的路径来列，而不是把整机所有互连的标称值相加。

NIC（Network Interface Card）和 RDMA 语境中的 HCA（Host Channel Adapter）都指主机侧的网络适配器，但驱动暴露的 RDMA device 是软件设备对象，其数量与物理卡数没有固定对应关系。同样，RDMA 逻辑端口也不一定是某一个物理网口，更不是 TCP/UDP 端口号。后面的聚合场景，就是这种区别产生实际影响的地方。

QP（Queue Pair）由 RDMA 的发送队列与接收队列组成，应用向它提交通信工作。软件另外封装的 Channel 往往管理连接和相关资源，但 Channel 不是组成固定的 RDMA 标准对象。一个 Channel 管理几个 QP，仍由软件决定。这样逐层拆开后，“加几个线程”“加几个 QP”和“加几条物理链路”才不会混成同一种扩容。

LAG（Link Aggregation，链路聚合）把多条成员链路组织成一个逻辑链路。Linux bonding 能向上提供这样的逻辑接口，LACP（Link Aggregation Control Protocol）负责与对端协商和维护聚合关系，但不规定必须把单个流平均拆到所有成员。在支持 RoCE（RDMA over Converged Ethernet，以太网上的 RDMA）聚合的硬件与驱动上，一个逻辑 RDMA 设备或端口也能承载多条物理成员。Linux bonding 文档与 NVIDIA RoCE LAG 说明

取两条各 100 Gb/s 的链路作为简单例子，选择相同速率只是为了看清聚合关系。它们的单向名义总量是 2 × 100 ÷ 8 = 25 GB/s。如果一个流被分配到其中一条，其吞吐就不能按两条相加，多个流也要实际分布到两条成员上才有聚合收益。具体 RoCE 的分配还取决于硬件与驱动，不能把普通 TCP bonding 的流分配规则直接当作 RDMA 保证。因此，看到一个逻辑端口或一个总计数，都还不能得知各物理成员分别承担了多少流量。

逻辑缓存块不是一段连续内存

缓存可以按连续 token 分块管理，物理数据却按模型层、K/V 张量和并行分片存放。以本文的 32 层模型为例，假设每层的 K 和 V 分开保存，一个 token 块在每个数组中各占一段连续区域，那么同一个逻辑块就对应 32 × 2 = 64 个张量片段，而不是一整段内存。这里的 64 来自层数和 K/V 两种数组，并不是任何传输库的默认批量。

网卡不理解这些片段属于哪一层、哪个 token。搬运需要的是源地址、目标地址和长度等描述，模型布局则决定怎样把逻辑块映射成这些字节范围。两端采用不同布局或精度时，还要另行转换，因为复制字节并不会自动改变数据的解释方式。

这样就能看出 数据量 / 带宽 省略了什么。同样 4 GiB，少量大段与大量小片段占用相同的有效载荷字节，却不一定有相同的描述、提交和完成处理成本。相邻片段能合并、传输接口能批量提交时，可以摊薄部分成本，但片段数与最终硬件请求数也就不再一一对应。量化缩放参数等辅助数据还会改变实际搬运量。只对齐总字节数，而没有对齐布局和提交形态，两次“带宽”就未必在比较同一类工作。

流水化可以隐藏时间，但不能消除工作量

单 GPU 算例中，网络需要 107.4 ms，Host→GPU 复制需要 85.9 ms。把 4 GiB 均分成 16 块，每块就是 256 MiB，选择 16 只是为了展示一个已经有多块并行、又容易手算的流水线。每块网络接收耗时 107.4 / 16 ≈ 6.71 ms，往 GPU 复制耗时 85.9 / 16 ≈ 5.37 ms。

第一块接收完成后，开始复制它，同时接收第二块。因为 5.37 ms 小于 6.71 ms，在没有额外共享争用的假设下，GPU 复制端总能赶在下一块接收完成之前腾出来。网络收完最后一块，还需把这一块复制到 GPU。用未取整的字节数计算，整份数据的就绪时间为 4 GiB / 40 GB/s + 256 MiB / 50 GB/s ≈ 112.7 ms，而不是串行中转的 193.3 ms。

分层缓存的职责与生命周期

每一层保存什么，取决于下一次访问

有了搬运预算，分层就不只是把设备按快慢排个序。活跃 KV 在后续 decode 中反复读取，历史前缀等待未来的同前缀请求，暂停请求的 KV 则决定它什么时候能恢复。访问频率和生命周期不同，每层保存这些状态的理由也就不同。

位置或路径 适合承担的职责 主要约束
HBM 保存活跃 KV，服务后续反复读取。 受单卡可用容量限制，要与权重、其他中间张量和算子工作区共同预算。
本机 Host DRAM 保留供本机后续复用的前缀，接住临时换出和提前预取。 恢复仍需经过 GPU 接入路径，还要考虑 NUMA 位置和内存读写竞争。
远端 DRAM 在多个推理实例之间共享历史 KV。 命中不等于立即可用，恢复需要消耗网络带宽并承担排队。

这些层次可以组合，却不要求每份 KV 层层留副本。一次性消费的数据可以直接进入目标 HBM，供本机后续复用的数据才有额外保留 Host 副本的理由。公开系统也有不同侧重：SGLang 推理框架的 HiCache把 GPU、Host 与共享存储组织成缓存层次，Mooncake 则研究共享 KV 与推理调度的结合。它们说明了这类分层的用途，但不能脱离各自负载直接套用收益。HiCache 设计文档

从目录命中到状态可用

跨请求复用还需要定位状态。假设缓存系统维护一份位置目录，记录各节点上报的前缀，那么目录给出的是候选位置，实际缓存块仍由数据节点持有。类似于分布式存储的位置元数据，目录与数据的更新不是同一个事件。

例如节点在上报之后淘汰了某段前缀，新状态尚未到达目录，此时目录仍会给出已经失效的候选。读取需要在数据节点确认有效范围，并持有相应数据直到访问结束。否则，即使目录与节点刚刚一致，也会在“找到块”和“开始搬运”之间出现回收竞态。

一次完整复用可以理解为：定位候选数据，确认并持有源块，为目标 GPU 准备相应空间，完成传输和消费端同步，然后从有效命中边界继续计算。查找、分配和交换地址属于控制面，搬运 KV 载荷属于数据面。控制消息远小于 KV，并不意味着等待控制操作的时间也可以忽略。GDR 减少了数据面的中转，没有把控制面一并消除。

反过来，保存结果时，目标已经持有的连续前缀也不必再次传输。只有缺失部分确实完成写入，新增的可用范围才成立。这里的增量保存是在避免向同一目标重复写入，并不意味着整个集群只保留一份副本。

保存历史前缀与临时换出，不是同一种提交语义

把同一份 4 GiB 从 HBM 复制到 DRAM，既能是在保存历史前缀，也能是在换出一个暂停请求。复制的字节相同，完成后承诺的事情却不同。

保存历史前缀，是为未来请求保留一份可复用的计算结果。这份数据是可重算的派生状态，不是数据库里必须持久化才能确认事务成功的日志。保存失败时，可以放弃这次缓存机会，让未来请求重新 prefill。为了找到可复用的数据，需要维护从前缀及其计算条件到缓存块的索引，但只有目标数据已经可用，才能把索引条目发布为可命中。

临时换出，是为了给仍未结束的请求腾出 HBM。如果调度器承诺之后从这份 KV 恢复，就必须在回收源块之前确认有可用的目标副本。换出失败时，要么保留源数据，要么明确转入重算，不能一边释放唯一副本，一边仍把请求记成“可以直接恢复”。

因此，保存完成、发布缓存、回收源块，是不同的事件。例如 HBM 块既被传输持有，又被另一个请求共享，复制完成只结束传输这一个使用者，不会结束另一个请求的使用。同理，恢复到 HBM 后，Host 副本只要还在服务其他请求，就不能随恢复完成一起释放。类似于异步 I/O 的缓冲区引用计数，I/O 完成和最后一个使用者退出之间，没有必然的等号。

前缀索引不能只对当前块的文本做 hash

标准因果 attention 中，一段 token 的 KV 依赖它之前的上下文。即使两个块包含相同的 token，只要前缀不同，也不能直接认为 KV 相同。因此，缓存身份至少要覆盖完整前缀关系，以及模型权重版本、位置和 attention 配置等影响计算结果的条件。实现上可以把父前缀身份和当前 token 块一起纳入索引键，而不是只对当前块独立取 hash。

例如，前缀甲后面接“你好”，与前缀乙后面接“你好”，最后两个字虽然一样，缓存身份仍应不同。vLLM 的公开前缀缓存设计把父块哈希、当前块 token 及额外隔离信息共同纳入块身份，表达的就是这个依赖关系。但“需要隔离”不等于“所有条件都必须直接塞进一个哈希”：模型版本也能通过独立命名空间隔离，关键是两个不兼容的状态不能落到同一个可复用范围内。

计算身份匹配，还要过物理表示这一关。同样的状态若按不同精度、张量布局或 TP/PP 分片保存，就不能直接把字节复制到目标地址。系统需要支持对应转换或重分片，不支持时就应拒绝这次复用。跨租户共享则另有授权边界，内容身份相同并不会授予访问权限。

按 token 块管理时，已填满并发布的块适合保持不可变，供多个请求共享。尾块仍在追加时，则需要区分哪些位置有效、哪些尚未产生。若允许共享一个之后还要写入的尾块，继续写入前就需要写时复制等隔离机制，不能改动其他请求正在使用的物理块。这里是可选的块管理方式，不把它当作所有引擎的共同实现。

块大小会同时影响索引数量、未填满空间和可复用的前缀粒度，但它不必等于网络传输块大小。前者是缓存管理单位，后者是 I/O 提交单位，而按层预取又有自己的计算就绪粒度。把这三个概念绑成一个大小，常常会让分配、带宽和流水线目标互相牵制。

NVIDIA 的 GDR 文档给出了一个具体的错误时序：GPU 上已经运行着一个 kernel，也就是 GPU 计算函数，与此同时网卡往它正在读取的区域写入数据。文档明确指出，这种并发读取没有正确的消费保证，GPU 允许观察到旧数据、部分写入或乱序的数据，即使网卡侧已经报告写入完成。因此，消费者需要通过平台规定的同步和工作提交机制排在相应写入之后，普通 CPU 内存屏障不能替代这个设备间顺序。

可见性、完整性校验和数据表示转换也应分开。同步解决 GPU 能否按约定观察写入，校验解决读到的数据是否通过指定检查，解压或布局转换则把它变成消费者需要的表示。一个校验 kernel 本身也是消费者，需要先满足读数据的条件，不能拿校验替代同步。若这些工作在 GPU 上执行，还会消耗执行资源和本地内存带宽，虽然传输本身采用了 GDR，这部分工作依然存在。

Stream 能表达操作的先后关系，但另开一条 stream 不会多出独立的计算单元或 HBM 带宽。因此，把恢复处理放进另一条 stream，只改变了依赖和调度方式，没有消除它与推理计算共享资源的事实。

内存池复用和连接复用省的是不同成本

拿到一段 Host 虚拟地址，还不等于设备已经能访问它。对常见的预注册内存池，预触页使实际数据页就位，固定页让设备访问期间的映射保持所需稳定性，RDMA 注册再建立设备使用的范围、映射与权限。进入请求路径以后，在池内分配缓存块，就不必每次重新完成整套工作。CUDA 的固定页内存说明

这个说法限定的是预注册池，不是所有 RDMA 内存访问都必须先固定全部页。ODP（On-Demand Paging，按需分页）允许支持它的设备与驱动按需建立页面访问，ibv_reg_mr 的公开接口就提供了相应注册选项。这里不展开 ODP 的设备支持与性能，只借它说明“注册”和“一次性固定所有物理页”不是同一个定义。ibv_reg_mr 手册

在长期使用的内存池中复用块，可以把其中一些成本摊到初始化或扩容，而不是每个请求重新承担。大页能减少管理同等内存容量所需的页数，但并不会替代 NUMA 放置、设备注册或访问同步。多张网卡各自注册同一份内存，也不意味着为每张卡复制了一份 KV，数据副本与访问映射应分别计数。NVIDIA 对 registration cache 的说明

连接复用处理的是另一笔开销：创建 QP 等通信资源、交换端点信息并建立可通信状态。类似于数据库连接池和 buffer pool，它们复用不同的对象。注册池已经存在，只说明内存这一侧的准备能复用，并没有证明连接也已存在，反过来也一样。因此，评估一次加载的准备成本，需要知道复用了哪一层资源，而不是只看高层接口是否叫“初始化”或“连接”。

复用也没有改变生命周期边界。仍被 DMA 或 GPU 消费的块不能重新分配，仍被设备访问的映射不能提前注销。设备直接访问省去的是 CPU 逐字节复制，而不是所有权与回收顺序。

Host 的需求主要来自希望保留的唯一历史 KV、临时换出的活跃请求，以及搬运缓冲和管理开销。可以先列成预算项：

“尚未包含”很重要：同一物理块兼任历史缓存和换出副本时，不能重复计算。如果为了可用性或局部性保存多份物理副本，又必须把每份占用算进去。压缩、共享与复制都应在物理块这一层落到账上，而不是仅靠逻辑 token 数相加。

历史缓存的容量收益，类似于数据库 block cache 的工作集分析。两次访问之间经过了多少不同的 KV 数据，决定了这份前缀在给定容量下能否留到再次使用。即便留住了，还要看这次命中替代了多少 prefill，以及加载花了多长时间。容量买到的是更长的复用窗口，不是固定比例的推理加速。

要报告 HBM:DRAM 配比，就在同一组推理实例的统计范围内，用实际分给 KV 的容量计算 H_KV:D_KV。共享 DRAM 池如果服务多组实例，需要统一按集群口径统计，或者明确各组配额，不能把同一份容量完整算给每一组。

公开整机规格也要按这个范围读。DGX B300 用户手册列出八张 GPU，以及默认 2 TB、最高 4 TB 的系统内存。系统内存是整机所有 CPU 的合计，不能拿它除以一张 GPU 的容量，得到所谓缓存配比。况且 Host 内存还服务操作系统与其他应用，HBM 还保存权重和工作区，硬件总容量并不等于缓存预算。

因此，没有一个脱离负载的最佳 HBM:DRAM 比例。如果前缀确实会再次访问，只因当前容量不足而提前淘汰，增加容量并让它留到复用时，就能避免这部分失效。若 HBM 装不下活跃工作集，更多 DRAM 只增加换出空间，并不减少每步的外部读取。若缓存已经命中，恢复队列却持续增长，缺的则是服务这些字节的能力。它们表面上都与“缓存不够快”有关，原因并不相同。

缓存的价值要按完成时间衡量

缓存命中不是最终目标

一次命中是否划算，要比较它省掉的 prefill 与新增的查找、排队、加载和同步。在其他排队条件相当、整份加载后再计算的情况下，只有这些额外等待短于被替代的前缀重算，才能直接降低这一次请求的首 token 延迟。若支持分块计算重叠，则要看实际依赖图上的关键路径，不能把所有时间机械相加。

这也解释了缓存位置与请求路由之间的关系。一个节点虽然命中更长的前缀，但如果它额外增加的恢复排队时间，已经超过多命中部分所节省的计算，它反而更晚输出。类似于带缓存局部性的数据库路由，局部性是输入条件，而不是必须坚持的绑定关系。目录报告的缓存容量也不等于实时可用空间，更不能代替计算与传输队列的状态。

保存时机又改变了谁承担这笔等待。生成后及时保存，能更早供其他请求复用，但先付出了带宽。推迟到回收 HBM 时再写，能避免一部分最终不再需要的历史保存，却把必要换出的传输放到了释放空间之前。时机可以改变，源块的生命周期不能省略，异步接口返回并不等于数据已脱离源内存。

因此，命中率不是缓存价值的完整度量。命中很短的一段前缀，与省掉整段长提示词的计算，都能记作“一次命中”，价值却不同。命中的 KV 字节、被替代的 prefill，以及保存后真正被再次使用的数据比例，更能说明容量换来了什么。单个请求的延迟与整机吞吐也要区分：省下计算资源能够帮助其他请求，并不证明这一次等待远端加载的请求也更快。

在途窗口与前台等待

KV 搬运不只与其他搬运竞争，也会进入推理正在使用的资源。例如 MoE（Mixture of Experts，混合专家）模型由路由机制为 token 选择部分专家子网络执行，专家分布在不同 GPU 时，需要分发输入、汇集结果。如果这些通信与 KV 搬运经过同一组网卡或 PCIe 路径，那么后台写回占用的服务时间，就会挤占前台通信的机会。当这种等待进入生成的关键路径时，写回自己的 GB/s 提高，ITL 却会变长。

在途字节量在这里按已提交、尚未归还窗口额度的载荷计量，直到系统处理完成通知并释放额度才扣除。它比任务数更能说明数据压力，因为一个小块和一份长上下文都能算作一个任务，字节量却不同。不过，大量小任务还有描述、提交和完成处理的开销，字节上限不能代替操作数上限。

固定块大小并进入稳定运行后，可以按 Little 定律理解平均在途量。目标吞吐是 B byte/s，一份工作从提交到释放在途额度的平均时间是 L 秒，那么平均占用约为 B × L byte。窗口至少要容纳这档在途工作，还需要考虑波动和批量提交。这里的 L 包含设备完成、通知处理与软件调度，不只是裸网络 RTT。

沿用 40 GB/s，再把完成周期设为 100 微秒，取这个整值只是为了把结果算到 MB 数量级。于是 40 × 10^9 × 100 × 10^-6 = 4,000,000 byte，即 4 MB，约 3.81 MiB。它不是某种设备的推荐窗口。这个推导说明，若硬件吞吐翻倍，而完成周期没有缩短，要支撑新的目标吞吐，平均在途量也得相应增加。

窗口过小会让设备在等待完成通知期间没有后续工作，窗口过大却不会突破物理路径上限，只会把更多任务堆进队列。此时不能拿已经被排队拉长的完成时间继续放大窗口，否则就是用拥塞产生的等待去证明还应增加拥塞。吞吐饱和之后，继续增加并发带来的主要变化往往是等待，而不是每秒多搬了多少字节。

恢复与保存也不是天然固定的前后台关系。历史前缀的额外副本可以晚些保存，但为了释放 HBM 而进行的必要换出，会直接影响下一个请求能否进入 GPU。真正决定紧迫性的是谁正在等这份状态，而不是操作的方向。优先级能改变谁先等待，不能凭空增加链路带宽。

带宽数字与推理收益之间还隔着什么

同一份数据，换一个计时区间就有另一种带宽

有效吞吐的分子都是载荷字节，分母却可以覆盖不同的工作。类似于存储测试，同一份数据仅除以读取区间，与除以“打开文件、读取、校验、关闭”的总时间，会得到不同的 GB/s。这不是哪个数字算错了，而是它们在回答不同的问题。

统计范围 纳入的工作 没有覆盖的等待或收益
RDMA 数据传输区间 两个计时点之间的数据传输，是否包含提交与完成等待由计时位置决定。 区间之外的查找、建连、数据准备或 GPU 就绪等待。
一次完整加载调用 这次调用负责的准备、数据搬运和收尾操作之和，具体范围由接口定义。 调用之前的排队，以及调用之后的推理计算。
一次请求的首 token 延迟 从请求发出到第一个输出 token 到达的完整等待。 后续生成的 ITL，以及其他并发请求是否受到干扰。

冷启动和稳态也有这层区别。第一次调用若承担内存就位、注册或建连，后续调用复用这些资源，两者就不是同一份工作。数据方向同样要明确：H2D（Host to Device）是 Host→GPU，D2H（Device to Host）是 GPU→Host。路径上的读写角色交换以后，一个方向的测量不能自动代表另一个方向。

单路成绩不能代替并发推理中的收益

空闲机器上的传输吞吐说明这条路径能做多少工作，真实推理中的 TTFT 与 ITL 才说明搬运是否值得。后台传输即使不用 GPU 计算单元，也仍会访问 HBM、PCIe 或网络。加入转换和校验以后，还会增加执行资源需求。把工作放进另一条 stream 或另一组 QP，并不会隔离这些物理资源。

因此，需要区分两组比较。在相同模型和请求负载下，增加保存或恢复以后，原来正在生成的请求慢了多少，反映的是搬运干扰。同一输入走“命中后加载”或“直接重算”，首 token 等待相差多少，反映的才是这次缓存收益。网卡利用率无法单独回答其中任何一个问题。

平均吞吐也不能替代延迟分布。多 GPU 中的一次慢分片或一次集中建连，若只影响少量请求，就能被平均数掩盖，却会落进这些请求的延迟。具体影响 P50 还是 P99，取决于出现频率和样本分布，不能笼统地说“偶发就一定出现在 P99”。短时突发与均匀到达即使拥有相同平均字节量，也会有不同的排队。

“任务入队、传输提交、后端完成、数据对 GPU 可用、计算开始”这些时刻，能把等待落回各自的原因。尤其是网口平均吞吐未满，只能说明观测窗口内的平均利用率不高，不能排除其中短时满载、拥塞或排队，更不能排除 Host 内存、共享 PCIe 与 GPU 就绪等待先卡住了供数。只有对应时间范围和数据路径，设备计数才足以支持归因。

把这些部分放在一起，我对 KVCache 的理解就不再是“给 GPU 接上更大的缓存”。它是在保留一份与计算上下文绑定的状态，并为下一次消费安排数据位置和到达时间。HBM 的价值来自活跃状态的反复读取，Host 与存储的价值来自更长时间内的计算复用。能否把后者转化成推理收益，还要经过两道约束：字节能不能及时到达，以及到达后消费者是否真的可以继续计算。
