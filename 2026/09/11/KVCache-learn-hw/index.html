学习 KVCache：硬件和架构

发表于 2026-09-11 |

KVCache 类似于数据库中的物化中间结果：保留已有状态能省掉计算，状态不在执行端时则需要搬回来。对大语言模型，这笔搬运还要看发生频率：开始生成时 load 一次，与每步 decode 都从外部取数，会产生不同的带宽需求。

这篇笔记用一份从模型参数推导出的 4 GiB KV，串起硬件路径、搬运成本和分层缓存的设计选择。产品参数来自公开资料，工作负载与有效带宽采用明确设定的算例。

KVCache 保存的状态与复用边界

这里的 KV 是 Transformer 注意力计算（attention）中的 Key 和 Value。文本经过分词器编码后成为 token 序列，token 是模型处理的离散单位，不与汉字或单词一一对应。在每层 attention 中，模型从各位置的输入表示生成 Query、Key 和 Value 向量，简称 Q、K、V。当前位置的 Q 与可见位置的 K 计算相关性，得到归一化权重，再用这些权重对 V 加权求和。

本文讨论的因果自注意力（causal self-attention），只允许一个位置使用自身及此前位置的信息。“因果”这个限制，正是历史 KV 能保留的原因：后面追加一个 token，不会进入已有位置的可见范围，也就不需要改变那些位置已经算出的状态。保持模型和输入条件不变，就能保存各层的 K/V，供后续计算继续使用。

Prefill 是处理本轮输入、建立对应 KV 的计算阶段。Decode 则利用已有状态逐步生成后续 token。本文默认采用稠密注意力（dense attention），即每个查询位置都关注其因果范围内的全部位置。在这个假设下，缓存消除的是历史 K/V 的重复计算，没有消除新位置对历史 K/V 的读取。这是后面带宽分析的起点。

因此，一份 KV 的身份不只由它对应的文字决定，还取决于这段文字之前的上下文。多层 Transformer 的后续层使用已经融合前文信息的表示，同一段 token 接在不同前缀后面，不能视为同一份完整 KV。位置处理也属于计算条件，模型用它表示 token 在序列中的顺序，改变位置或位置编码方式同样会影响复用边界。

后面的算例以活跃 KV 驻留 GPU 显存为基准。文中涉及的 GPU 使用 HBM（High Bandwidth Memory，高带宽内存），它是一种以堆叠 DRAM 和宽接口提供高带宽的内存技术。CPU 侧系统内存则记作 Host DRAM。这个区分说的是数据位置，HBM 本身也属于 DRAM。

上一轮的回答也会成为下一轮的前缀

Prefill 和 decode 描述的是计算阶段，不是两种永久分开的缓存。看一段连续对话就很直观：

“回答甲”上一轮是输出，这一轮已经成了输入的一部分。只要对应 token 的 KV 已经建立并保留，它就与之前的问题一样，属于本轮能够复用的历史状态。这里真正匹配的是编码后的 token 序列，角色标记、分隔符和对话模板也包含在内，不能只比较页面上显示的文字。vLLM 的前缀缓存示例

这段对话还藏着一个容易忽略的边界。在逐 token 的自回归生成中，模型先处理已有输入，产生下一 token 的分数，再从中选出一个 token。这个刚选出的 token 要作为下一步输入，才会建立自己的 K/V。如果生成恰好在选出它后结束，就不能把“已经输出”当作“已有 KV”。缓存按块发布时，还有完整块的边界。这里的缓存块是容纳一组连续 token 状态的管理单位，未发布的尾部不计入可复用范围。

反过来，即使输入的 KV 全部存在，也不等于能直接给出下一 token。KV 保存的是各层注意力所需的中间状态，不包含最终输出层的 logits，也就是各候选 token 在归一化成概率之前的分数。以截至 2026-10-15 查阅到的 vLLM 公开实现为例，它会为取得 logits 重算输入的末尾 token。如果输入长度恰好按块对齐，而该路径只接受完整块命中，就要回退最后一个块。这是该实现的消费边界，不是所有缓存都必须采用的策略。

所以，能够跳过多少计算，要看有效状态的边界以及引擎怎样消费它，不能拿已输出的文本长度直接代替。跨请求复用还多了一段生命周期：请求结束后保留状态，下次找到它，并在不位于目标 GPU 时完成 load。KV load 完成后，decode 反复读取的是本地状态，不是每生成一个 token 都从远端重传同一份前缀。

一份 KV 有多大

KV 容量由缓存张量的形状和元素大小决定。Attention head 是一组分别计算注意力权重和加权结果的向量通道，head_dim 表示该 head 中 Q/K 等向量的维度。以 GQA（Grouped-Query Attention，分组查询注意力）为例，Q head 被分组，同组的多个 Q head 共享一个 K head 和一个 V head。因此，缓存按 KV head 数计量。GQA 论文

对于 K、V 维度相同、各层采用相同配置的常规表示，有：

我选一组便于核算的参数：32 层、8 个 KV head、head_dim = 128，K、V 都以 BF16 保存。BF16 是一种 16 位浮点格式，每个元素占 2 byte。这组二次幂参数能让 token 数与 GiB 的换算保持直观，不指代某个线上模型。公式前面的 2 来自 K、V 两份张量，最后的 2 才来自元素字节数。

取 32,768 个 token，正好得到 4 GiB。再把长度缩为四分之一，也就是 8,192 个 token，就得到 1 GiB。并发示例选 64 个请求，是为了后面能按八个实例均分，每个实例承接八个请求。这些数字只负责让工作集的变化容易核算：

示例工作负载 推导 全模型 KV 有效数据量
一个请求，8,192 个 token 128 KiB × 8,192 1 GiB
一个请求，32,768 个 token 128 KiB × 32,768 4 GiB
64 个请求，各有 32,768 个 token，没有共享前缀 4 GiB × 64 256 GiB

这些是全模型 KV 的逻辑载荷，未计入块内碎片、索引、预留空间和并行布局中的复制。TP（Tensor Parallelism，张量并行）拆分同一层的张量与计算，PP（Pipeline Parallelism，流水线并行）则把不同模型层放在不同阶段。前者影响每个 GPU 持有哪些 head 或分片，后者影响它持有哪些层。只有确认数据没有额外复制、各分片又足够均衡，才能把总量按 GPU 数平均。

这条公式的边界在于“保存完整 K/V”。例如 MLA（Multi-head Latent Attention，多头潜在注意力）通过低秩投影把 K/V 信息压入较低维的潜在向量，而不是缓存每个 head 展开后的完整 K/V。DeepSeek-V2 的公开定义还缓存一份用于位置计算的独立 Key 分量，因此连“只数一个压缩向量”也不够，仍要列出实际保存的全部张量。DeepSeek-V2 论文中的 MLA 定义

KV 量化又是另一种缩减。它用更少的位数表示元素，使用缩放系数的方案还要保存这些辅助数据。这里改变的是 KV 表示，仅量化模型权重不会自动缩小 KVCache。vLLM 的量化 KVCache 说明

区分“复用计算结果”和“扩展活跃工作集”

前缀缓存（prefix caching）保留已经算好的前缀状态，供后续请求跳过相应的 prefill。它直接省掉的是输入计算，收益主要体现在 TTFT（Time To First Token，首 token 延迟），也就是请求发出到收到第一个输出 token 的时间。这个收益还要扣除查找和 load 的代价，而后续 dense decode 仍然需要读取历史 KV。vLLM 对前缀缓存收益范围的说明

Offload（卸载）则是把 KV 从 HBM 转移到 Host DRAM 或存储设备。暂停请求，之后将 KV swap-in 到 HBM 并继续驻留，是一种用法。HBM 始终装不下整个活跃工作集、每一步都从外部取数，是另一种用法。前者在请求 resume 前付出一次 swap-in 开销，后者会持续占用链路，类似于工作集超过内存后的反复换页。

本文用 load 表示把已有 KV 从 Host、远端或 SSD 搬入目标 GPU 缓存的操作。例如 vLLM 的 start_load_kv 接口负责将外部 KV load 到引擎的 KV 缓冲区。swap-in 特指把此前换出的 KV 搬回 GPU，resume 则指暂停的请求继续运行。KV 已被换出时，需要先完成 swap-in 并使数据对计算可见，请求才能 resume。

因此，复用历史前缀时，需要找到匹配的 KV，并把 GPU 外的数据 load 到 HBM。把装不进 HBM 的活跃状态长期留在外部，则让外部链路进入每一步生成的关键路径。两者使用相同的 KV 数据，却不能用同一种带宽预算评价。

HBM、PCIe 与网络的数据路径

历史 KV 不在目标 GPU 上时，问题就从“省掉多少计算”变成了“沿哪条路径把状态搬回来”。这里讨论 GPU、Host 和网卡通过 PCIe 连接的服务器，其他 CPU–GPU 互连需要另算。为避免容量与带宽混用进制，下面统一用十进制 GB/s、TB/s 表示带宽，软件容量用二进制 GiB、MiB、KiB，分别对应 2^30、2^20、2^10 byte。网卡的 Gb/s 按 bit 计量，换成 GB/s 要除以 8。

GPU 封装内的 HBM 与访存路径

HBM 与 GPU 计算单元之间的距离很近，但它不是 GPU 裸片上的缓存。一个 HBM 堆叠由多片 DRAM 裸片（die）垂直叠放而成，裸片指封装前的单块半导体芯片。在 B200/B300 这类产品中，HBM 堆叠与 GPU 计算裸片同处一个封装，通过高密度互连连接。中介层（interposer）是这种封装中用于芯片间高密度布线的结构之一。Micron 对 HBM 结构的介绍

所以，“GPU 用 HBM”和“网卡往 GPU 搬数据”不是同一条路径。图 1 将外部搬运和封装内访问画在同一个示意中：

图 1：外部数据经 PCIe 进入 HBM，GPU 计算则经封装内的内存接口读取 HBM。

图左的网卡可以是本文讨论的 CX 系列，例如 CX-7、CX-8。这里的蓝色箭头落在 GPU 的 PCIe 接口上，标的是接入 GPU 的那一段链路：HGX B200 的 GPU 通过 Gen5 接入，DGX B300 则由 CX-8 通过 Gen6 连接 GPU。以 DGX B300 为例，从 Host 搬数据时，前面还经过 CPU→CX-8 的 Gen5 链路，因此完整路径是“Host→Gen5→CX-8→Gen6→GPU”。从 CX-8 接收到的网络数据出发，进入 GPU 走的是其中的 Gen6 这一段。HGX B200 接入规格与 DGX B300 拓扑

假设命中的 KV 保存在 Host 或远端，它先从图左侧经过 PCIe 进入 HBM。等 KV load 完成且数据可用，计算沿绿色的封装内路径读取本地 KV，不再经过 PCIe 或网卡，命中片上缓存时连 HBM 也不用访问。这就解释了表里的两种带宽为什么不能互换：PCIe 衡量跨设备搬运，HBM 带宽衡量本地内存接口。SXM 只是 GPU 模块的安装与连接形态，并不是 GPU 到 HBM 的协议。

规格里的“单 GPU 合计带宽”是同一个 GPU 的各个 HBM 内存通道之和。通道内的读写共享数据线，不同通道则能并行调度，因此 7.7 TB/s 不是“同时读 7.7、再写 7.7”，也没有预先分成固定的读写份额。纯读可以利用这份总带宽，混合读写则要共同分配它，并承担方向切换等开销。这里相加的是并行通道的能力，不是把 HBM、PCIe 和 GPU 间互连这些不同路径的带宽相加。

PCIe 的 lane、链路宽度与带宽换算

PCIe lane 是相邻两个 PCIe 端口之间的一条全双工串行物理通路，由一对发送差分信号线和一对接收差分信号线组成。差分信号利用一对线之间的电压差表示信号，两对共四根数据信号线合起来才是一条 lane，如图 2 所示。

图 2：一条 lane 的物理组成。TX、RX 分别表示发送与接收，加减号标识差分对的两根信号线。

图中没有画参考时钟和地线。PCIe 链路由一条或多条 lane 组成，×16 表示这条链路使用 16 条 lane，Gen5/Gen6 表示代际，两者回答的是不同问题。器件一共有多少 lane，也不能代替某一段链路的宽度：两条 ×16 连接不是一条 ×32。数据在 lane 之间的分配由 PCIe 硬件完成，应用不会为某块 KV 指定“走第几条 lane”。PCIe 物理层与链路宽度概述

图 3：×16 链路的结构示意。每条细线表示一条完整的双向 lane。

PCIe 5.0 每条 lane 的单向速率是 32 GT/s，这是规范标注物理层传输速率的单位，G 表示十亿，T 是 transfer。Gen5 使用 NRZ（Non-Return-to-Zero，不归零）二电平信号，一个符号表示 1 bit。它每秒发送 320 亿个符号，因此这时的符号率 32 Gbaud、规范标注的 32 GT/s 和原始比特率 32 Gb/s，在数值上恰好相同。Gbaud 计量每秒发送多少个符号，每个符号承载几 bit，则由信号编码决定。

换算只需要把单 lane 速率乘链路宽度，再扣掉编码开销。128b/130b 编码表示每传输 128 bit 内容需要占用 130 bit 链路空间。Gen4 的每 lane 速率是 16 GT/s，Gen5 是 32 GT/s，于是：

到了 Gen6，变化集中在信号传输和数据组织两个方面：

  1. PAM4 让每个符号携带更多 bit。 PAM4（四电平脉冲幅度调制）用四种电平状态表示 00、01、10、11 这四种取值，因此一个符号能携带 log₂4 = 2 bit。Gen6 的符号率仍为 32 Gbaud，但每个符号携带的信息翻倍，单 lane 单向原始比特率就成为 32 × 2 = 64 Gb/s，规范将这一代的速率标为 64 GT/s。沿着“符号率→比特率→字节带宽”换算，×16 链路得到 32 × 2 × 16 ÷ 8 = 128 GB/s 的单向原始带宽，双向合计为 256 GB/s。这里的翻倍来自每个符号承载的信息增加，计算已经使用 64 Gb/s 时，PAM4 的这份收益就已经包含在内。CX-8 手册中的 PCIe Gen6 速率

  2. FLIT 与 FEC 改变了数据组织和纠错方式。 TLP（Transaction Layer Packet，事务层数据包）承载设备的读写请求及返回数据，包中既有载荷，也有地址、操作类型等协议字段。Gen6 用固定长度的 FLIT（Flow Control Unit，流控单元）组织这些信息，并加入 FEC（Forward Error Correction，前向纠错）冗余来修正传输错误。因而，刚才算出的 128 GB/s 要由载荷、协议字段和纠错信息共同使用，应用实际搬运 KV 的速度还要扣除这些开销。Gen5 的 128/130 对应另一套线路编码，Gen6 的载荷效率需要按其 FLIT 格式和实际事务组合计算。PCI-SIG 的 FLIT、PAM4 和 FEC 说明

现在把同一份 4 GiB 放在这两条路径上计算。如果数据完整经过本地 HBM 接口，按 7.7 TB/s，纯读的理想时间约为 4 × 2^30 / (7.7 × 10^12) ≈ 0.558 ms。从 Host 经过 Gen5 ×16 搬入，单是 PCIe 的理论时间就约为 4 × 2^30 / (63 × 10^9) ≈ 68.2 ms，按取整后的带宽相除约差 7,700 / 63 ≈ 122 倍。这个差值不是一次 attention 的加速比，它只说明跨过 PCIe 边界以后，同样的字节量进入了另一档时间预算。

GPUDirect RDMA 省掉了哪一段

RDMA（Remote Direct Memory Access，远程直接内存访问）允许适配器访问注册并授权的内存区域。以单边 RDMA Write 为例，发起方提交远端地址与访问凭据，接收端不需要由 CPU 逐字节接收、再复制这份载荷。注册建立的是设备可使用的地址映射和权限，并不是制作数据副本。GPUDirect RDMA把这类设备访问扩展到 GPU 显存，让接收网卡直接写入 GPU，而不必先落到 Host DRAM。

三条路径的终点相同，区别在于数据是否经过网络、是否在接收端 Host 留下一份中转数据。

下文把 GPUDirect RDMA 简写为 GDR。它在这组比较中省掉的是接收端 Host 中转，源端取数、网络和 GPU 接入链路仍然存在。类似于存储系统里的零拷贝，关键是少做了哪一份工作，而不是给整条路径贴上“没有复制成本”的标签。

这条路径也由设备的连接方式决定。PCIe 交换器（PCIe switch）是连接多个 PCIe 端口、按地址和路由转发事务包的硬件，类似网络交换机承担的转发角色，但这里处理的是 PCIe 事务。网卡与 GPU 接在同一个交换器下，而且平台允许设备间对等转发时，事务可以直接在交换器内到达 GPU，省去 Host 中转。跨 CPU socket 的设备访问则还要经过 CPU 间互连，并满足平台的对等访问支持。判断 GDR 路径时，需要沿设备之间经过的连接来分析。NVIDIA 对 GDR 路径和拓扑的说明

CX-8 的端口模式与 PCIe 接入带宽

CX-8 的 800 Gb/s 描述网络侧的总速率。一次 KV 搬运能用到多少，还取决于这些速率分布在哪些端口，以及载荷经过怎样的 PCIe 连接。把网络入口和设备接入放到一起，才能解释整卡带宽如何变成一次 load 的带宽。

800G 首先要落实到端口模式。InfiniBand 是面向高性能互连的网络体系，与 Ethernet 不是同一套链路协议，XDR 是其中的速率代际。官方列出的 CX-8 C8180 支持单端口 800G XDR InfiniBand，其 Ethernet 模式则支持两个 400GbE 端口，C8240 的默认模式也是 2×400GbE。在这些 Ethernet 模式下，2 × 400 ÷ 8 = 100 GB/s 是两端口的单向合计，单独使用一个端口只能对应其中一半。CX-8 端口配置

PCIe 一侧，CX-8 支持 Gen6 ×16。若实际连接为 Gen5 ×16，经过这段连接的载荷就受前面算出的约 63 GB/s 单向上限约束。假设网络与一条 Gen5 ×16 恰好串在同一次搬运路径上，仅比较这两段的理论能力，就是 min(100, 63) = 63 GB/s。若两端都以 Gen6 ×16 接入，PCIe 的单向原始上限提高到 128 GB/s，才有条件承接 100 GB/s 的网络载荷，实际吞吐再由内存、协议开销和共享资源决定。

目标 GPU 的接入也按同样方法核算。一份数据最终进入一张 GPU，就要经过那张 GPU 的接口。分到多个 GPU 时，每路独立的连接能够分担载荷，共用的上行则仍只提供一份带宽。这与网卡有几个端口一起，决定了整机并发传输能使用多少资源。

延伸阅读：Socket Direct 为网卡提供两组 PCIe 接入。支持这一配置的 CX-8 型号可以通过主卡、辅助卡及连接线，把两组 Gen5 ×16 分别接入主机，聚合它们的 I/O 能力。在双路服务器上，这也能让两侧 CPU 分别访问自己的网卡接口。它是一种具体的硬件接法，需要配套型号与插槽。CX-8 的主机接口与 Socket Direct 说明

根端口是主机侧 PCIe 层次结构的起点。从 CPU 向下读图，先到交换器朝向主机的上游端口，再由朝向 GPU 的下游端口接出。CPU→CX-8 这一段是 Gen5，CX-8→GPU 这一段是 Gen6，两段分别建立链路、协商速率和宽度。

Host 向本机 GPU 复制 KV 时，事务由 CX-8 的 PCIe 交换部分从 Host 侧转到 GPU 侧。这是本地复制，不使用网卡的 RDMA 功能。

网络数据直达 GPU 时，目标 CX-8 接收数据并直接写入 GPU HBM，经过它的 PCIe 交换部分，这条路径使用 GDR。若网络数据先写入目标 Host DRAM，后半段就仍需一次 Host→GPU 本地复制。

因此，计算本机 Host→GPU 的搬运能力，要同时列出 Gen5 和 Gen6 两段，再找其中的限制。计算远端直达，则沿“源端内存→源端网卡→网络→目标 CX-8→目标 GPU”展开，目标 CPU 的 Gen5 链路不在这条载荷路径上，源端的内存和 PCIe 却仍然在。这是按路径预算带宽的具体做法。

NVLink 是 GPU 等处理器之间的高速互连，NVSwitch 是连接这些链路的交换器。它们与这里的 PCIe 交换器不是一回事。KV 若直接到达负责消费的 GPU，load 无需再绕 NVSwitch。若采用另一张 GPU 转发，才需要计入那段 GPU 间传输。带宽预算要按实际经过的路径来列，而不是把整机所有互连的标称值相加。

布局与提交开销

以上算例只按字节量计时。实际缓存按 token 块管理，内存却按模型层和张量排列：以本文的 32 层模型为例，若每层 K、V 分开存放，一个 token 块就在 32 × 2 = 64 个数组中分别对应一段数据。

传输需要把这些片段变成源地址、目标地址和长度。相邻片段能合并时，提交开销可以摊薄，因此同样 4 GiB 的少量大段与大量小段，会有不同的 CPU 和设备队列开销。比较吞吐时，要同时记录总字节数、片段数和提交批量。

搬运频率、排队与推理延迟

一次 load 与每步 load

如果 KV 在每步 decode 后都被移出 HBM，下步就需要重新搬入。沿用 4 GiB 和 40 GB/s，只统计这份固定前缀，比较接下来 100 个 decode 步骤。取整百是为了直接看出重复搬运的影响：

KV 的使用方式 外部传输次数 累计搬运量 累计链路占用时间
开始时 load，之后一直驻留 HBM 1 4 GiB 约 107.4 ms
每步搬入，用完后腾出 HBM 100 4 GiB × 100 = 400 GiB 400 × 2^30 / (40 × 10^9) ≈ 10.74 秒

前一种方式每步读 HBM，外部 load 主要增加首 token 前的等待。后一种方式持续依赖外部供数，会限制 ITL（Inter-Token Latency，相邻输出 token 的间隔）。重叠能减少等待，但不会减少搬运量。部分 KV 常驻 HBM 时，按实际需要从外部读取的部分计算。

load 与重算的时间比较

缓存命中后，请求仍要等 KV 可用。要判断是否值得 load，需要比较省下的 prefill 时间与新增的查找、准备、传输和同步时间。

固定模型、输入及 GPU 执行条件，以“前缀 KV 已在 HBM 中可用”为共同基准。假设直接 prefill 比这个基准多花 300 ms，外部缓存的查找、目标块分配及同步合计花 20 ms。两者是演算参数，用整值便于展示等待如何抵消收益。300 ms 在实际系统中应由相同输入的两种执行方式测得。

对前面那份 4 GiB KV，传输花 107.4 ms。如果整份 load 后再计算，且其他调度等待相同：

处理方式 相对基准多出的时间
直接 prefill 300 ms
命中后立即 load 20 + 107.4 = 127.4 ms

这次 load 能让首 token 提前 300 - 127.4 = 172.6 ms。172.6 ms 也就是它能容忍的额外排队时间。若 load 前排队 200 ms，总等待变成 200 + 127.4 = 327.4 ms，比直接重算晚 27.4 ms。选择 200 ms，就是为了越过这个临界点。

因此，请求路由需要比较各候选节点上的计算等待与 load 等待。按层预取时，则记录每层 KV 就绪和计算开始的时刻，把真正阻塞计算的等待计入首 token 延迟。

持续请求与后台 I/O

单次 load 足够快，还需要能跟上持续到达的请求。对同一个方向，稳定服务要求：

40 GB/s 每次搬 4 GiB，纯传输服务能力约为 40 × 10^9 / (4 × 2^30) ≈ 9.31 次/秒。若每秒持续到达 10 次这样的 load，供数需求已经超过服务能力，队列会不断增长。增加 DRAM 容量只让更多 KV 留得住，不能消除这段传输排队。

KV 搬运还会与推理竞争 I/O。例如 MoE（Mixture of Experts，混合专家）把 token 路由到部分专家子网络。专家分布在不同 GPU 时会产生 I/O。当它们与 KV 搬运共用网卡或 PCIe 路径，并因带宽竞争发生等待时，后台保存就会延长前台通信，增加 ITL。

为将带宽留给正在等待数据的请求，需要限制后台传输的提交量。不过，为释放 HBM 而进行的必要换出，也会阻塞新请求入场，应按它所阻塞的计算安排优先级。

分层缓存的数据复用与生命周期

各层保存的数据

每步都读取的活跃 KV 需要高带宽，等待下次复用的历史前缀则更需要容量。这两种访问频率决定了各层的主要用途：

位置 主要用途 容量或访问约束
HBM 保存活跃 KV，供 decode 反复读取。 占用权重和工作区之外的显存空间。
本机 Host DRAM 保留历史前缀、临时换出的请求和预取数据。 经 GPU 接入路径 load，受 NUMA 和内存竞争影响。
远端 DRAM 在推理实例之间共享历史 KV。 需要网络传输，并承担 load 排队。
NVMe SSD 保留更冷的历史 KV。 在搬运路径上增加设备读取。

P/D 分离让不同 GPU 分别承担 prefill 和 decode，prefill 结束后将 KV 交给 decode 侧。如果只服务这次生成，KV 可以直接到达 Decode GPU。

是否额外保留 Host 副本，取决于之后是否还会复用它。SGLang HiCache把 GPU、Host 与共享存储组织成多层缓存，Mooncake则研究共享 KV 与推理调度的结合。

前缀身份与不可变块

共享历史 KV，首先要识别同一份计算结果。前缀甲后接“你好”，与前缀乙后接“你好”，即使末尾 token 相同，KV 仍依赖各自的前文。因此，一个块的身份需要包含父前缀及当前 token 块，模型版本、位置处理等计算条件也要处于相同的复用范围。vLLM 的前缀缓存设计通过父块哈希与当前块 token 等信息表达这种依赖。

对于跨请求的历史缓存，这里选择只共享完整、不可变的块。未填满的尾块由当前请求继续持有，填满后再发布。这样省去了共享尾块的写入隔离，代价是匹配前缀时少复用不到一个块的尾部，需要补算这部分。

从目录命中到 GPU 可用

假设位置目录记录了各节点上报的前缀。节点上报后淘汰了某块，而目录尚未收到更新，新的请求就会找到一个已经失效的位置。即使查询时数据还在，若它在查询之后、传输之前被回收，load 也会读到错误的内存。

因此，需要在数据节点确认可用范围，并在同一个受保护的操作中取得这些块的使用引用。引用覆盖传输期间，淘汰流程才能知道哪些内存尚不能回收。目录负责定位候选，数据节点负责确认并持有实际数据。

目标端还有另一条边界：GPU kernel 正在读一块内存时，网卡同时写它，即使网卡已报告写入完成，kernel 也能观察到旧数据、部分写入或乱序结果。NVIDIA 的 GDR 文档明确要求用相应的同步和工作提交机制保证设备间顺序。

保存完成与源块回收

把 KV 从 HBM 保存到 Host，有两种目的。历史缓存为未来请求省计算，保存失败可以放弃这次缓存机会，等未来重新 prefill。临时换出则要为当前请求腾显存，如果还承诺它能 swap-in 并 resume，就必须先确认目标副本可用，才能回收源块。

两种情况都要求数据就绪后再发布为可命中。传输结束可以释放传输持有的引用，若还有其他请求读取同一块，内存仍需保留。这个回收条件与异步 I/O 缓冲区相同：最后一个使用者退出后才能复用。

HBM 与 DRAM 的容量预算

容量预算要容纳前面那些数据及其生命周期。HBM 需要保留正在参与 decode 的 KV，能分给它的空间为：

模型计算产生的中间张量称为激活。若从模型加载后的空闲显存开始记账，已占用的权重就不再扣除。

沿用 64 个请求、每份 KV 4 GiB、没有共享前缀的假设，活跃 KV 共 64 × 4 = 256 GiB。八个单卡模型副本均分请求，每卡需要 256 / 8 = 32 GiB 的 KV 载荷空间。实际预留还要覆盖生成过程中新增的 token 和块内空余。TP/PP 部署则按每张卡持有的实际分片计算。

同一物理块同时用于历史缓存和临时换出时，只占一份空间。反过来，同一份内容在 HBM 和 Host 各保存一次，就各占一份。假设 HBM 有完整的 4 GiB，Host 已有匹配的前半段，即 128 KiB × 16,384 = 2 GiB，补齐后的账目是：

统计量 结果
本次新增搬运量 4 - 2 = 2 GiB
Host 中可复用的 KV 4 GiB
两层的 KV 载荷总占用 4 + 4 = 8 GiB

因此，增量保存节省传输，物理副本决定容量。压缩或共享块会改变占用，预算应按实际分配的字节计量。

历史前缀的复用距离

保留多少历史 KV，才会让下次请求命中？可以看两次使用同一前缀之间，缓存还访问了多少其他数据。

设五份互不共享的历史前缀 A、B、C、D、E，各占 4 GiB。为了只观察容量的作用，假设以整份前缀为单位，采用 LRU 淘汰，访问未命中时将该前缀放入缓存，忽略元数据开销。访问顺序为：

比较能存四份的 16 GiB 与能存五份的 20 GiB：

访问进度 16 GiB 缓存 20 GiB 缓存
读完 A、B、C、D 保留 A、B、C、D 保留 A、B、C、D
再读 E A 最久未访问，被淘汰 五份全部保留
再读 A 未命中，需要重算或从更低层取得 命中，可以 load

两次访问 A 之间，其他不同前缀占 4 × 4 = 16 GiB。这就是本例按字节计的复用距离。要在 LRU 下保住 A，还需加上 A 自己的 4 GiB，因此达到 20 GiB 时，这次访问才从未命中变成命中。

新增容量的收益由访问序列决定。如果之后不再访问 A，多保留它就省不下计算。即使命中，仍要代入前面的 load 账目：本例不排队时省 172.6 ms，排队 200 ms 时反而多等 27.4 ms。

并发、复用与带宽共同决定 HBM:DRAM 配比

HBM 要容纳同时活跃的状态，DRAM 要覆盖值得保留的历史，两者由不同的负载特征决定。把前面的算例放在一起，就能看到比例怎样变化：

负载变化 容量或时间的变化 对配比的影响
活跃请求从 64 个降为 32 个，每份仍为 4 GiB HBM 的 KV 载荷从 256 GiB 降为 128 GiB 历史访问序列不变时，DRAM 需求可以保持不变。
历史缓存从 16 GiB 扩为 20 GiB 在上述序列中，A 从被淘汰变为保留 提高命中能力，活跃 KV 的 HBM 需求不变。
40 GB/s 路径持续收到每秒 10 次、每次 4 GiB 的 load 需求超过约 9.31 次/秒的服务能力 增加 DRAM 无法消除排队，需要减少搬运需求或增加有效带宽。

所以，配比应从请求并发和长度求 HBM 需求，从历史前缀的访问序列求 DRAM 需求，再检查传输是否能满足 TTFT 和 ITL 的目标。同样的硬件，改变并发或复用模式就会得到不同需求，因此没有脱离负载的最佳 HBM:DRAM 比例。

报告配比时，用同一组推理实例实际分给 KV 的容量 H_KV:D_KV。共享 DRAM 池服务多组实例时，应按整个池对应的实例集合统计，或按各组实际配额统计。

整机规格补充：DGX B300 用户手册列出八张 GPU，以及默认 2 TB、最高 4 TB 的系统内存。这是整机硬件容量。估算 KV 配比时，需要从系统内存中扣除其他用途，并从各 GPU 显存中扣除权重和工作区，再在相同实例范围内相加。

并发与测量补充

在途窗口与资源复用

限制后台提交量，需要同时看在途字节和操作数。在途字节量是已经提交、尚未完成并归还窗口额度的载荷总量。字节窗口约束数据压力，操作数上限约束大量小片段带来的提交和完成处理开销。

稳定运行时，Little 定律给出平均在途量约为 B × L：B 是目标吞吐，L 是从提交到归还额度的平均时间。沿用 40 GB/s，假设完成周期为 100 微秒，得到 40 × 10^9 × 100 × 10^-6 = 4 MB，约 3.81 MiB。100 微秒是用于算例的整值，L 包含通知处理与调度时间。

窗口需容纳这部分工作，才能让设备持续有数据可传。设备已经持续满载时，再扩大窗口会增加排队，此时应观察前台等待是否增加。

准备操作也能占用 load 时间。预注册内存池把页面就位、固定页和 RDMA 注册摊到初始化阶段，连接池则复用 QP（Queue Pair，RDMA 的发送与接收队列对）和已交换的端点信息。它们分别减少内存准备与建连开销。CUDA 固定页内存与 GDR registration cache

带宽的计时范围与推理收益

同一份数据，除以纯传输时间与除以整个 load 调用时间，会得到不同的吞吐。沿用前面的 4 GiB 算例：

计时范围 时间 有效吞吐
只计传输 约 107.4 ms 约 40 GB/s
加上 20 ms 准备与同步 约 127.4 ms 4 × 2^30 / 0.1274 ≈ 33.7 GB/s

减少准备时间会提高第二个数字。测量时需要注明是否包含排队、内存注册、建连与同步，并区分 Host→GPU 和 GPU→Host 的方向。

判断单次复用的收益，就固定模型和输入，比较 load 与重算的 TTFT。判断搬运干扰，则在相同请求负载下加入后台搬运，观察正在生成的请求的 ITL 增加多少。

记录入队、提交、接收完成、GPU 可用与计算开始的时间，才能把等待落到对应阶段。并发测试还需观察延迟分布，避免平均吞吐掩盖少数慢分片或突发排队。
